## 嫌疑链与技术假说

**时间线实锚**（backend.log ✅亲核）：前一进程 15:46:17–15:59:22 每 30s 一条 `网络检测失败：判定为离线`（learning_scheduler.py:336，4 天累计 3899 行）→ 此后日志静默 4 分钟 → 16:03:47 进程蒸发 → 看门狗重启 → 10 分钟内再崩三次。

**代码事实**（learning_scheduler.py:311-337 ✅亲核）：
1. 一探 socket 连裸 IP 223.5.5.5:53，3s 超时**有效**；
2. **二探回退 `urllib.urlopen("https://www.baidu.com")`——主机名需 DNS 解析，而 getaddrinfo 在 Windows 上不受 timeout 参数保护**：网络栈半死（VPN/虚拟网卡/适配器复位）时可阻塞远超 3s 甚至无限挂起——**最强假说**；
3. 缓存 10s + tick 30s 驱动 → 每 tick 最多付 6s 阻塞 I/O；刷屏 17 分钟说明网络持续半死，静默 4 分钟与"探测挂死在 getaddrinfo"吻合；
4. 待确认项（方案第一步）：check_network 的调用线程模型（tick 在事件循环内直调还是已卸载线程池）——决定挂死拖死的是整个后端还是单线程。

**备选假说**（一并装探针排除）：socket.close() 在异常栈下挂起；tick 持锁互等；WER 强杀（无痕退出码）。

## 二、影响面
- #1/#2/#5：仅 learning_scheduler 网络检测内部，消费方只有 tick 的 pause/resume 判定——最坏影响=网络感知延迟 +几秒；
- #3：进程级 faulthandler，无性能开销（仅触发时写文件）；注意与现有日志体系并行不冲突；
- #4：launcher 崩溃快照格式加字段，crash_forensics 消费方（人工排障）向后兼容；
- #6：heartbeat_history.jsonl 每行 +2 字段，前端无消费该文件，零 UI 影响。
- **不改**：tick 线程模型本身（若第一步查明是事件循环直调，追加卸载为 #2 的一部分，同样在拍板圈内）。

## 三、验证方法
1. **静态哨兵（新测试）**：模拟离线（monkeypatch socket 失败 + urlopen 挂起不返回）断言 join 超时路径返回 False 且线程被弃；断言退避后 warning 间隔；
