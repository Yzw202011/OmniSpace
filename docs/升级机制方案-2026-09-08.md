# OmniSpace 应用内升级机制方案（2026-09-08）

> 状态：**待拍板**（方案四段制成文，用户拍板前不改任何代码）
> 需求原话：未来 v3、v4 版本升级，用户只需下载升级包，拖到软件指定目录下，
> 在设置页点"升级"（支持导入已下载的升级包），软件自己完成升级。

---

## 〇、大白话总括

给软件配一个"给自己做手术的小医生"：

- **为什么需要小医生**：软件正在运行时，自己的代码文件被系统锁着（就像人没法给自己做手术），所以换文件这件事必须由一个**独立小程序（updater）**在软件完全关机后进行，换完再把软件叫醒。
- **用户全程只有三步**：① 从发行渠道下载升级包（一个 `.upg` 文件，通常 40MB~几百 MB）；② 把它拖进软件目录下的 `updates` 文件夹（或在设置页直接导入）；③ 设置 → 软件升级 → 点"开始升级"。之后软件自己关、自己换文件、自己重启，回到界面时已是新版本。
- **防伪**：每个升级包带 Ed25519 签名（和激活码同款技术），包内每个文件都有 SHA256 指纹。假包、被改过的包、放错版本的包，一律拒绝并说明原因。
- **绝不变砖**：换文件前先把旧文件全部备份；万一中途断电/崩溃，下次启动自动还原成旧版本照常使用。用户数据（`data/` 目录：激活状态、对话记录、作品）**永不被升级触碰**。

## 二、总体设计

### 2.1 组件分工

```
┌─ 开发侧（我们用）──────────────────────────────┐
│ tools/make_upgrade_package.py                    │
│  两个构建目录(old/new) → 文件级差分 → 签名 → .upg │
│  （差分基准=两边的 dist_manifest.json，现成的）    │
└──────────────────────────────────────────────────┘
                        │ 用户下载 .upg
                        ▼
┌─ 用户侧（随软件出厂）────────────────────────────┐
│ <安装根>/updates/            ← 用户拖包的指定目录  │
│ backend/api/upgrade.py       ← 设置页背后的 API   │
│ backend/services/upgrade_service.py ← 验签/扫描   │
│ frontend Settings「软件升级」节 ← 拖拽导入+列表    │
│ updater/updater.py           ← 小医生（独立进程）  │
│ launcher/boot.py 恢复钩子     ← 断电自愈          │
└──────────────────────────────────────────────────┘
```

### 2.2 升级包格式（`.upg`，本质是 zip）

```
OmniSpace-upgrade-2.4.0-to-3.0.0.upg
├── upgrade_manifest.json   # from_min/from_max/to_version/to_build_id、
│                           #   files[]{path,size,sha256,action=replace|delete}、
│                           #   contains_migration、payload_bytes、created_at
├── upgrade_manifest.sig    # Ed25519 签名（对 manifest 规范化字节）
├── README.txt              # 更新说明（用户可读的更新日志）
└── payload/                # 待落位文件，镜像安装根相对路径
    ├── backend/…  frontend/dist/…  launcher/…  skills/…  modelxiazai/…
    ├── pydeps/…            # 仅含新增/变更文件（自动差分）
    └── dist_manifest.json 等# 根文件（新版本全量清单，落位后成为新身份）
```

- **默认包含范围**：代码全量 + pydeps 自动差分；`runtime/`（python 本体）、`tools/`（ComfyUI）、`models/` 默认**不含**（体积大头且低频变动，需要时打包工具可显式 `--include runtime` 开启）。
- **多级跳版**：manifest 声明 `from_min~from_max` 版本区间（如 2.4.0 ≤ 当前 < 4.0），区间外拒绝；v2.4 用户可直接升 v4，无需逐级。

### 2.3 用户点击"开始升级"之后发生什么（时序）

1. 后端三道预检：签名+每文件 sha256 验证 ✕ 版本兼容 ✕ 磁盘余量（≥payload×2.2）；任一不过直接拒绝，系统零改动。
2. 检查有无正在跑的任务（图片/视频队列、训练、对话生成）——有则拒绝并提示先等完成或取消。
3. 后端用 `runtime\py310\python.exe` 拉起 **updater 独立进程**（DETACHED_PROCESS，脱离进程树，后端死了它活着）。
4. 前端切到全屏等待页："正在升级到 vX，请勿关闭窗口/断电"，每 3 秒探测后端心跳。
5. updater 等 2 秒让后端把响应发完 → POST splash `/api/quit` → 等整链退净（后端 5800-5835 + 启动页 + ComfyUI 全灭，宽限 90s，退不净则放弃升级、零改动）。
6. **备份**：所有将被替换/删除的旧文件按原路径复制进 `updates/backup/<时间戳>/`；若包声明含 DB 迁移，额外快照 `data/omnispace.db(+wal/shm)`。
7. **落位**：payload 逐文件复制替换（os.replace 原子换名，只读属性先清，失败重试×3）；执行删除清单；updater 自身文件最后落位；全程写 `updates/state.json` 状态机 + `updates/logs/upgrade_*.log`。
8. **验证启动**：updater 用桌面快捷方式同款命令拉起 Boot exe → 等后端健康（冷启动宽限 300s）→ 核对 `/health` 的 build == manifest 目标 build_id。
9. 成功：清工作目录、旧备份只留最近 1 份；等待页探到心跳恢复 → 自动刷新 → 用户看到新版本。
   失败：**自动回滚**（backup 还原 + DB 快照还原）→ 重新拉起旧版 → 状态记为 failed/rolled_back，设置页可查原因。

### 2.4 断电自愈（boot 恢复钩子）

`boot.py` 启动最前端读一次 `updates/state.json`：若处于 backing_up/applying/verifying_start（上次升级被打断）→ 调 `updater/restore.py` 从备份还原 → 启动页日志说明"上次升级中断，已自动还原为 vX" → 照常启动旧版。正常路径只多读一个 json，零开销。

### 3.3 验证方法（验收前置，实弹为准）

**批1（生成侧+校验核心）**：
- `pytest backend/tests/unit/test_upgrade_service.py test_updater_apply.py` 全绿（签名往返、篡改任一字节被拒、zip-slip 路径穿越被拒、兼容矩阵、假目录 apply/回滚）。
- 手工：造两个临时假构建目录 → `python tools/make_upgrade_package.py --old A --new B` 产出 .upg → 解包核对 manifest 差分正确、验签通过。

**批2（后端 API+前端 UI）**：
- 起后端，curl 六端点信封格式合规（success/data/error 结构，ADR-01）。
- 真浏览器：设置页见"软件升级"节；导入一个小真包 → 列表出现"可升级"；导入篡改包 → 徽章"签名无效"；**不点开始升级**（无危险操作）。

**批3（updater 本体+boot 钩子+打包白名单）**：
- 隔离目录命令行干跑：对假安装目录执行完整 替换→验证→回滚 循环。
- boot 钩子单测：伪造中断 state.json → 调钩子 → 断言还原。

**批4（全链实弹，最终验收）**：
- 用 make_dist 出两个假版本真构建（如 2.9.9 → 3.0.0-test1，改 config.yaml 版本号+一处前端文案）→ 打升级包。
- 旧构建复制到隔离目录当"用户安装"→ 正规链启动 → 真浏览器走完整流程：导入→开始升级→观察自动退出→文件替换（目录 diff 取证）→自动重启→`/health` 返回 3.0.0-test1→等待页自动刷新。
- **故障注入三连**：① 篡改包内一字节 → 拒绝且系统零改动；② apply 中途强杀 updater → 重新双击启动 → 自动还原旧版正常使用；③ 错误私钥签的包 → 拒绝。
- 回归：`tools/run_tests.py` 全量 + 前端 tsc/eslint/vitest/build 四闸。
- GPU/ComfyUI 零涉及（纯文件操作），不触碰 GPU 测试门禁。

| # | 风险 | 对策 |
