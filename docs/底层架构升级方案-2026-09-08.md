### 2.2 ComfyUI Dynamic VRAM（官方博客 + GitHub Discussion #12699 + Releases）

- 机制：**模型权重不再 RAM+VRAM 双份常驻**，按需在两级间调度——官方称「大减 RAM 占用，NVIDIA 上普遍提速，升级 RAM 已无必要」。
- 版本线：功能早于 v0.26.0 就存在（v0.26.0 已有「别关 dynamic vram」提示语）；**v0.34.0（我们正在用的版本）起 ROCm 7.14+ 默认开启；CUDA/NVIDIA 侧默认状态 release notes 未明说** 🔶——**这是 V2 要上机核实的第一件事**。
- 对我们的特殊价值：① 32G RAM 机器上 RAM 双份占消除 → 提交内存闸门（A2）压力直接变小（静默死亡根因是提交内存耗尽）；② qwen-image 流式模式 28G+ RAM 场景缓解；③ 已含在用版本里的收益：v0.32 **H3 峰值内存修复（#15486）+ MiniMax-H3 VAE 优化（#15446）**、v0.31 **LTX/Wan 提速（#15138）**、v0.33 CUDA Graphs（#15570）——**全部无需改动，只需实测取证确认生效**。

### 2.3 量化与显存（多来源交叉）

- **AWQ W4A16**：权重减半（8B ≈4.5~5GB），但 vLLM 中 AWQ kernel **只支持 float16 不支持 bfloat16**；且运行时显存大头是 KV cache 与激活（可达权重的 2~3 倍）→ gpu_memory_utilization 与 max_model_len 的分档钳制比换量化更关键。
- **FP8（含 FP8 KV cache）**：需计算能力 ≥8.9（Ada/Hopper+）→ **5070 Ti 可用、3060 基线档不可用** → 必须按硬件档路由，不能全局开。
- **Wan2.2 GGUF + TeaCache + 步数跳跃**：社区实测 16G 卡 30 分钟内出 5~6s 视频（Q4_K_M）；8G 卡配步数跳跃 5 分钟级——为 B-阶段三补档与 12G 基线档提供工程手段（本方案不展开，归 B 层）。
- Qwen3.5 AWQ 官方量化已有现成件（kaitchup 评测：精度相近、思考量不损）⚠️ 待上机。

### 2.5 第二轮摸底新增情报（并发会话，2026-09-08，来源见文末）

**① MTP 投机解码（vLLM 官方特性线）**
- Qwen3.5 原生 MTP 头 vLLM 已支持（无需另配草稿模型）；单用户低并发（=我们的场景）是投机解码收益最大区间（vLLM 官方文档定调）⚠️。
- 外部实测参考：Qwen 系 MTP-3 接受率 57~59%、c=4 档 +36%（27B FP8 档）；EAGLE-3 峰值 3~4×——全部 ⚠️ 非本机。
- **已知雷（诚实必须写）**：GitHub #53912——**prefix caching + MTP 在 hybrid Mamba/GDN 模型上输出损坏，v0.28.0 仍未修复**（#43559 关而未愈）。我们的 qwen3.5 正是 GDN 混合架构且现开 `--enable-prefix-caching`（vllm_service.py:572）→ **V6 冒烟必须设「关前缀缓存」对照组**；若 MTP+缓存共存无解，则二者取一拿实测数字拍板。
- VL 多模态 + W4A16 + MTP 三重叠加无公开先例 → 冒烟不过就放弃，零产品影响。

**② FP8 KV cache（与 V3/D4 衔接）**
- vLLM 官方 2026-04 博客定调 production-ready：KV 内存约减半、精度损失 <1%、长上下文延迟斜率更平 ⚠️。
- 与 V3 的关系：V3 已按硬件档路由（sm_120 开 / sm_86 不开）——第二轮补一点：**FP8 KV 同时是长上下文（16K/32K）开闸的前置**，V3 落地时建议把 max_model_len 16K/32K 两档 config 化一并做（32K 压线与否上机才知道，压线停在 16K）。

**③ torch 2.13 + cu130**
- 官方 2.12 起 CUDA 12.8（cu128）弃用转 13.x；sm_120 在两条线都支持；Blackwell 的 SageAttention/FlashAttention 预编译轮子已有 cu130 档 ⚠️。
