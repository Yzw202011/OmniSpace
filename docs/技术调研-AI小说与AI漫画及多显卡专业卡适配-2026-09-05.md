## 〇、一句话结论

三个方向都有成熟参照物，不用从零摸索：**写小说**的成熟套路是「分层大纲 + 世界观库/RAG + 章节流水线」，咱们现成的知识库（RAG）和对话引擎正好是地基；**画漫画**的角色一致性有顶会开源方案，其中三个已做成 ComfyUI 插件，咱们的 ComfyUI 底座可以直接挂；**多显卡/专业卡**最大的坎有两个——本仓库代码是「全系统一张卡」的写法（记账、互斥锁、调度全部锚死 0 号卡），以及 vLLM/NCCL 专业卡生态基本只在 Linux 上——最顺的路是给引擎层加「远程推理服务器」形态，桌面端连过去，而不是把整个 Windows 发行版重做一遍。

### 1.2 可借鉴的六个架构模式

1. **分层生成**：故事大纲 → 卷/幕 → 章节细纲 → 正文，逐层细化、逐层可改。这是所有长篇项目的共同骨架，解决「单次上下文写不了长文」的根本问题。
2. **世界观库 + RAG**：人物卡、地点、设定、前文摘要入向量库，写到第 200 章时检索注入。**咱们已有 knowledge_service + 学习模块（正在做五道质检闸升级），地基现成**。
3. **一致性账本**：伏笔登记/回收、角色状态（受伤/易容/死亡）、时间线校验（show-me-the-story、goink 的核心卖点）。
4. **多智能体流水线**：策划/写手/审校分角色，审校负责质量闸（neuro-book、NovelClaw）。
5. **人在回路介入点**：每层大纲、每章正文都留「AI 生成→人工改→继续」的交互，纯自动成书质量不可控是共识。
6. **生成质量与上下文是资源问题**：长上下文 + 高质量生成吃显存，与 §三/§四 的多卡、专业卡诉求正好咬合（16GB 卡现在 max-model-len 只有 4K/8K 档，多卡/80G 卡后可开 32K+）。

### 1.3 映射到 OmniSpace

- **不需要新推理引擎**：小说模块纯编排层，复用现有对话引擎（vLLM）即可；接入点走品类注册表 `register_engine_module()`（src/services/inference/base_engine.py:111-125）最多注册一个「novel」品类做权限/调度归类。
- **新建的是工作台**：后端编排（大纲树、章节队列、伏笔账本、角色卡）+ 前端写作台。角色卡/世界设定可复用学习模块的知识库表结构和质检闸（批 2~3 的注入质量闸对小说 RAG 同样适用）。
- **风格/题材**：可复用风格包治理的思路做「文风包」（提示词模板 + 金标准快照防漂移）。

### 2.2 五条技术路线评估

- **A 角色一致性**（StoryDiffusion/StoryMaker/IP-Adapter 族 🔶）：漫画的命根子。咱们漫剧模块已有「参考图锚 + P0 三件套」（见记忆：分镜一致性诊断），StoryDiffusion 属于同方向的升级件，且**已有 ComfyUI 插件版，挂工作流即可试用**。
- **B 分镜→版面流水线**（ai-comic-factory 思路）：LLM 分镜 → 逐格出图 → 拼页排版 → 对话框/文字排版。咱们漫剧的分镜表结构（storyboard_rows）和生图统一队列可以直接复用，缺的只是「页排版 + 对话框」环节。
- **C 中间帧插值**（ToonCrafter）：关键帧 → 动态过渡，可反哺漫剧视频链路（动镜）。
- **D 线稿上色**（MangaNinja）：如果产品定位是「画漫画（可编辑线稿）」而非「漫剧（视频）」，线稿产线 + 精确上色是刚需路线。
- **E 一体化生成**（DiffSensei）：学术最前沿但**无许可证**，只读论文借鉴思路，勿直接抄代码。

### 2.3 映射到 OmniSpace

- 漫画模块 = 漫剧的姊妹模块：复用资产库、风格包、分镜表、生图队列、ComfyUI 生命周期管理（comfy_proc.py 统一管理器）。
- 三步走建议🔶：①先挂 ComfyUI_StoryDiffusion 验证角色一致性效果（半天级 PoC）；②再补「页排版+对话框」流水线（参考 ai-comic-factory 的版面思路）；③按产品定位决定要不要线稿产线（MangaNinja）。
- 多格并行出图天然吃多显卡：每张卡跑一路生图 = 产出线性翻倍（见 §三）。

## 三、多显卡支持

### 3.1 本仓库现状体检（✅ 代码探查，2026-09-05）

结论：**当前是「全系统一张卡」架构**，五块差距：

1. **显存记账没有设备维度**：vram_manager `get_usage()` 读 `torch.cuda.memory_allocated(0)`（src/engines/vram_manager.py:214）、`get_available_mb()` 读 `mem_get_info(0)`（:239）；vLLM 准入闸门同样只看 0 号卡（src/engines/vllm_service.py:351）。
2. **功能锁是全机互斥**：`_VALID_FEATURES = (dialog, paint, video_gen, training)` 四功能互斥（src/middleware/feature_lock.py:23-30）——隐含「只有一张卡可抢」，多卡本可以「绘画占 1 号卡、对话占 0 号卡」并行。
3. **vLLM 无多卡参数通道**：启动参数只拼 dtype/max-model-len/gpu-memory-utilization 等（vllm_service.py:539-558），**没有 --tensor-parallel-size，也不设 CUDA_VISIBLE_DEVICES**；util 按 16GB 消费卡写死分档 0.85/0.87（vllm_backend.py:56-92）。
4. **ComfyUI 单实例铁板**：端口单例（comfy_proc.py:39）、进程管理器模块级单例（:386-397）、绘画与 H3 共用同一实例；ComfyUI 主程序在 Windows 下默认强制绑 0 号卡（tools/ComfyUI_windows_portable/ComfyUI/main.py:48-52）。
5. **双卡雏形已存在但没人用**：`enumerate_gpus()`/`resolve_device_plan()` 已能枚举全部卡（src/engines/gpu_backend.py:348-436），config 有 GPU_PRIMARY_DEVICE/GPU_AUXILIARY_DEVICE/GPU_SECONDARY_OFFLOAD 三参数（src/config.py:90-92），但目前只喂给 /hardware 展示接口（api/hardware.py:242），引擎侧零消费。

### 3.2 业界三条路线（✅ 官方文档/仓库）

| 路线 | 代表 | 解决什么 | 对咱们的改造代价 |
|---|---|---|---|
| **张量并行 TP** | vLLM `--tensor-parallel-size N`（流水线并行 PP、多机加 Ray） | 单卡装不下的大模型切到多卡 | vLLM/NCCL 生态要求 Linux🔶；参数通道 + 显存语义重做（"整卡预算"→"多卡预算"） |
| **多实例分卡** | ComfyUI `--cuda-device N` + 端口池；vLLM 每卡一实例 | 功能级并行：绘画/对话/小说各占一卡同时干活，吞吐线性涨 | 与现有 feature_lock 模型最贴——把「全机互斥」改「按卡分配」；需 per-GPU 显存账本 + ComfyUI 多实例生命周期 |
| **分层 offload / 工作流切分** | ComfyUI-MultiGPU（DisTorch2：把权重分层摊到多张"捐赠卡"）✅；ComfyUI 官方内置 MultiGPU CFG Split（多卡同时采样，官方实测 ≈1.95x）✅ | 显存不够借邻居卡 / 单工作流提速 | 插件级/工作流模板级，几乎不动架构；但 DisTorch 牺牲速度换容量，CFG Split 只覆盖采样段 |

### 3.3 推荐组合（待拍板）

1. **第一步（架构账本）**：把显存记账/准入闸门/遥测加上 device 维度（per-GPU 账本），功能锁从「全机互斥」升级为「功能→卡」资源域。这是所有路线的地基。
2. **第二步（多实例分卡）**：ComfyUI 端口池 + `--cuda-device` 绑卡，多卡机器上绘画/视频并行；vLLM 按卡绑定实例。
3. **第三步（按需）**：装不下的大模型用 vLLM TP（专业卡/Linux 场景）；ComfyUI 侧挂 MultiGPU 插件或官方 CFG Split 提速。

## 四、专业卡（A100/H100）适配

### 4.1 硬件/精度矩阵（✅ vLLM 官方文档与社区资料）

| 卡 | 架构(CC) | BF16 | FP8 | vLLM 建议 |
|---|---|---|---|---|
| RTX 5070 Ti（现机） | Blackwell(12.0) | ✅ | ✅原生 | FP8 可用 |
| A100 40/80G | Ampere(8.0) | ✅全速 | ❌无原生 | BF16 或 INT8 W8A8；FP8 只能 weight-only 降级 |
| H100/H200 | Hopper(9.0) | ✅ | ✅原生 | FP8 W8A8 最佳档 |

- **好消息**：咱们仓库的精度×量化档位矩阵已有 `cuda-ampere+` 档（src/engines/gpu_backend.py:178-203），A100/H100 按 CC 号会自动落 bf16 全开档——**精度适配基本现成**。
- **要改的口径**：vllm_src/vllm_service 里按 16GB 单卡标定的 util 分档、KV 预算、让渡/准入阈值（0.85/0.87、4K/8K 上下文、显存 ≥8GB 分档等），需改为按「卡数×单卡显存」推导。

### 4.2 平台现实

- vLLM 官方以 **Linux** 为主要支持平台（✅ 官方文档/部署资料）；NCCL（多卡通信底座）无官方 Windows 支持🔶。**A100/H100 的标准栖息地是 Linux 服务器**（多卡常配 NVLink + InfiniBand，vLLM 文档的 TP/PP/多机玩法全部基于此）。
- 咱们的 Windows 发行形态耦合点：backend+launcher 共 **57 处/16 文件**（✅ 探查）——launcher 全链（taskkill/CREATE_NO_WINDOW/powershell/版本检测）、vLLM 杀进程树（vllm_service.py:806-818）、ComfyUI Windows Job Object（comfy_proc.py:109-134）、single_instance 命名互斥体、license_gate powershell 指纹等。
- **三个现成的好底子**（✅ 探查）：① vllm_service 杀进程已有 POSIX 分支（:816-827）；② BaseEngine 协议注释明说为「子进程/远程形态」预留了 health_check/graceful_stop/vram_reclaim_gb 钩子（base_engine.py:227-249）；③ Linux 上 vLLM 官方支持 sleep mode——现在「Windows 下 sleep mode 不可用被迫停进程让渡」的 hack（vllm_service.py:223-263）在 Linux 反而自然消掉。

### 4.3 两条路线（待拍板）

- **路线甲：远程推理服务器模式（推荐）**。A100/H100 服务器上跑 Linux 官方 vLLM（OpenAI 兼容 API）/ComfyUI（HTTP API），OmniSpace 桌面端通过 BaseEngine 新增「远程引擎」形态连过去。改动集中在：①对话后端路由层加一个 RemoteBackend（现有 `backends/base.py` 路由层就是为这类扩展留的）；②ModelManager 台账/显存概念扩展「远端引擎」条目；③设置页加服务器地址配置。桌面端 Windows 代码基本不动。
- **路线乙：整体出 Linux 服务器版**。launcher/single_instance/license/打包链全重做，成本数倍于甲，且短剧/绘画的桌面体验（pywebview 壳、任务栏进度）在 Linux 要重验。除非有明确的"整套部署到机房"需求，否则不建议先行。
