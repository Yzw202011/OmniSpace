# OmniSpace 插件开发规范 v1.3（统一要求，2026-09-16 拍板；09-17 v2.1 单文件交付修订 + v1.2 技能声明；09-18 v1.3 对表修订）

> 适用对象：为 OmniSpace 开发插件的所有开发者（含第三方）。
> v1.3（2026-09-18，响应 issue #4 合作方对表反馈）：manifest 全字段表
> 与三套版本号口径、四类白名单（+llm.provider）、generic 边界厘清、
> 事件主题命名约定、route 非必填。
> 本规范分**机器闸**（导入时自动检查，不过即拒）与**审查闸**（入出厂
> 登记时人工逐行审查）两层；出厂级插件两闸都要过，用户导入级机器闸必过。
> 基类契约详见 `src/cutemamen/plugin.py`（单一真源，2026-09-16 统一）。

## 1. 两种插件形态与信任档

| 形态 | 内容 | 信任档 | 导入要求 |
|---|---|---|---|
| 纯数据包 | `.CuteMamen` 包（manifest + 权重 + 记忆），`base_model` 必须是**已知四类**之一（rust.coding / cubegpt.face / lora.adapter / llm.provider——末项 2026-09-17 v0.9.1 跟版新增，OpenAI 兼容端点外挂；video.making 已随 video-making 插件移除） | 用户·纯数据 | 直接导入，无需确认 |
| 带源码包 | `.CuteMamen` 包**内嵌源码**（source/plugin.py，v2.1），可实现全新插件类型——用户只需导入这一个文件 | 用户·含源码 | 必须通过源码静态安检 + 用户显式确认 |
| 出厂插件 | 上述任一形态 + 走 PR 逐行审查 + 入 `_SEED_PLUGINS` | 出厂·已审查 | 仓库内代码级登记 |

**base_model 边界（v1.3 厘清）**：基类默认 `BASE_MODEL = "generic"` 仅为
占位——不在注册表四类内的 `base_model`（**含 generic**）若不带源码，导入
即拒（`PLUGIN_SOURCE_REQUIRED`）；含源码档 `base_model` 任意（保留默认
generic 亦可，源码在场即生效）。

## 2. 源码硬性要求（机器闸：AST 静态安检，命中即拒）

1. **必须**定义 `ExpertPlugin` 的子类，并实现 `on_think(event, ctx)`；
   导入写法用双路垫片（两条加载路径等价）：
   ```python
   try:
       from .plugin import ExpertPlugin, PluginContext
   except ImportError:
       from omnispace.plugin import ExpertPlugin, PluginContext
   ```
2. **禁止导入**（含 from 形式）：`subprocess` `socket` `urllib` `urllib3`
   `requests` `http` `httpx` `ctypes` `pickle` `multiprocessing`
   `importlib` `webbrowser` `ftplib` `smtplib`。
3. **禁止调用**：`eval()` `exec()` `compile()` `__import__()` `open()`；
   以及 `os/shutil/sys` 的 `system/popen/kill/exec*/spawn*` 与任何对象的
   `unlink/rmdir/removedirs/makedirs/mkdir/startfile/write_text/write_bytes/
   read_text/read_bytes` 属性调用。
4. 允许的依赖面：标准库安全子集（`json/math/time/typing/dataclasses/
   collections/threading` 等）+ `numpy` + `PIL`（仅图像处理，不落盘）。
5. 确需文件 IO / 网络 / 子进程能力的，不写在插件里——向宿主提案
   桥接接口（走 PR 讨论），由宿主以受控方式提供。

## 3. 运行契约

- **事件入**：`on_think({"topic": str, "data": spec}, ctx)`；`data` 由
  调用方定义（如 video 的 keyframes/shots、rust 的 code）。
- **结果出**：返回 JSON 可序列化 dict（str/int/float/bool/小 dict/list）；
  **帧序列走专用 `frames` 键**（ndarray 列表）由宿主落盘，绝不塞进其他
  键——大数组进 JSON = 内存红线（POC2-A 实测 1080p 帧列 1.2GB）。
- **事件广播**：`ctx.emit(topic, payload)` 只发摘要与统计；topic **原样**
  发布（无强制前缀），自定义主题建议以 `plugin.<name>.` 开头防撞名。
- **结果通道（自动）**：`on_think` 返回值由宿主内核发布到固定主题
  `plugin.<name>.output`（其他插件可订阅）——插件自己不要往该主题 emit。
- **记忆**：working 用 `memory.set/get`；蒸馏知识用 `remember/recall`；
  事件流水由基类自动记录。不越权读写宿主状态。
- **资源**：纯 CPU；**不加载模型、不碰 GPU/显存**（显卡是独木桥，
  调度归宿主）；自报 `memory.footprint`，内存预算超限会被内核 LRU 淘汰；
  单次执行软超时默认 180s（调用方可覆写），超时插件置故障态。
- **生命周期**：`on_load(ctx)` 初始化、`on_unload()` 释放，幂等可重入；
  任何钩子抛异常都会把插件置故障态（unload 后可复位）。

## 3.1 技能声明（v1.2，2026-09-17 技能插座批0）

插件可在 manifest.json 声明 `skills`，声明后即可在对应创作功能页的
「插件技能」入口被用户**显式调用**（不做 LLM 自动调用）：

```json
"skills": [{
  "id": "polish-dialog",
  "feature": "chat",
  "title": "台词润色",
  "description": "按指定文风润色当段对白",
  "input": "text"
}]
```

- `feature` 白名单：`chat`（AI对话）/ `novel`（写作台）/ `comic`（AI漫画）
  / `manga`（漫剧创作）；`input` 种类：`text` / `image`；
- 单插件技能数上限 **4**；`id` 规则同插件名 `^[a-z0-9][a-z0-9_-]{0,63}$`；
  `title` 必填；`description` ≤500 字（超长截断）；
- 非法 `skills` 字段**导入即拒**（`PLUGIN_SPEC_MISMATCH`）；
- 含源码插件也可在类上声明 `SKILLS`（首次加载时采纳并回写登记面；
  包 manifest.json 的 `skills` 字段优先）；
- 技能调用统一走各功能端点（已上线：`POST /dialog/skill`、
  `POST /novel/chapter/{chapter_id}/skill`、`POST /comic/skill`）或通用
  invoke，运行契约（三道闸/信任三档/沙箱/数据最小化）与本规范 §3 完全一致；
  技能查询接口：`GET /api/v1/plugins/skills?feature=chat|novel|comic|manga`。

## 4. 包格式（`.CuteMamen` = tar.gz，机器闸强校验）

```
<Name>.CuteMamen (gzip tar, ≤64MB, ≤64 条目)
├── manifest.json          # 必填 name/base_model（route 缺省=插件名）；全字段见下表
├── weights/weights.npz    # numpy 权重（allow_pickle=False 读）
├── memory/
│   ├── working.json       # {"entries": [{"key","value"}, ...]}
│   ├── episodic.json
│   └── semantic.json
└── source/plugin.py       # v2.1 可选：内嵌源码（新类型插件必附，≤256KB；
                           #   在场即按含源码档走安检+确认门）
```
条目白名单仅上述 6 个路径，多余条目=拒。

**manifest.json 全字段表（v1.3；`build_manifest` 实际出线 14 项）**

| 字段 | 谁写 | 说明 |
|---|---|---|
| `name` | 开发者 | 必填；规则 `^[a-z0-9][a-z0-9_-]{0,63}$` |
| `base_model` | 开发者 | 必填；纯数据包必须 ∈ 注册表四类（§1），含源码档任意 |
| `skills` | 开发者 | §3.1 技能声明（类 `SKILLS` 或 manifest 直填，后者优先） |
| `route` | 自动 | 缺省 = 插件名（内核按它路由事件），无需手填 |
| `capability` / `author` / `version` | 自动（可覆盖） | author 默认 "DistributedFormer"，建议覆盖为自己的标识 |
| `standard_version` | 自动 | 恒 "2.0.0"（DF 上游包格式标准，随包携带） |
| `core_version` / `min_core_version` | 自动 | DF 上游内核版本口径（"0.8.7"）；OmniSpace 只登记不消费 |
| `memory_budget` | 自动 | 打包时内存足迹估算（字节）；OmniSpace 只登记不消费 |
| `lifecycle` / `memory_levels` / `format` | 自动 | 机器元数据（钩子名单/记忆层级/包格式标识） |

**版本号口径（三套，互不相干，v1.3 说清）**：本规范 v1.x = 文档版本；
manifest `standard_version`（2.0.0）= DF 上游 CuteMamen 包格式标准；
宿主 OSP 运行时另有自己的方案版本线。DF 专属字段在 OmniSpace 导入闸
**只登记不参与逻辑**（loader 决策在案）——第三方对接以本规范为准。

打包示例：

```python
from src.cutemamen import save_pkg
from src.cutemamen.rust_coding import RustCodingPlugin
# 纯数据包（已知类型的权重/记忆变体）
save_pkg(RustCodingPlugin("my-rust"), "my_rust.CuteMamen")
# 带源码包（新类型插件：源码一并打进包，用户单文件导入）
save_pkg(MyPlugin("my-plugin"), "my_plugin.CuteMamen",
         source_py=MY_PLUGIN_SOURCE_TEXT)
```

## 5. 开发者工作流

1. 参照 `src/cutemamen/rust_coding.py` 写源码（本规范 §2-3）；
2. 本地自测：套用 `tests/unit/test_plugin_runtime.py` 的夹具模式
   （`load_plugin_module` + `find_plugin_classes` + 直调 `on_think`）；
3. `save_pkg` 打包 → 设置页「插件」导入（或用户手动放包）；
4. 想成为出厂插件：提 PR——机器闸全过 + 维护者逐行审查（对齐
   RustCoding 登记审查口径）+ 入 `_SEED_PLUGINS`。

## 6. 用户侧须知（设置页文案基线）

- 蓝徽章=出厂·已审查；绿徽章=用户·纯数据（不引入新代码）；橙徽章=用户·含源码
  （**将在软件内部直接运行，请只安装信任来源**——导入时需勾选确认）；
- 用户插件上限 32 个、源码单文件 ≤256KB、包 ≤64MB；
- 导入只需选一个 `.CuteMamen` 文件——新类型插件的源码由开发者打进包内（v2.1）；
  包内带源码时后端会要求确认，确认后按橙色档登记；
- 用户插件文件存于 `data/plugins/imported/`，删除即清场。
