# 显存深度优化方案书（四段制，2026-09-14 深夜）

> 排期依据：用户令「显存独木桥无法消除物理约束，尽量深度优化」。
> 本方案基于当日系统显存画像实测（数据见 §一），全部为**零下载、零新依赖**的软件优化。

## 一、实测画像（2026-09-14 数据）

| 场景 | 显存占用 | 备注 |
|---|---|---|
| 空载（全模型释放） | **2567MiB** | 桌面+驱动+残余 CUDA context |
| 启动基线（backend 起、无用户任务） | **11076MiB** | 含 bge 嵌入 CUDA 预载 + warmup 链 |

| **GPU 进程数** | **25 个** | WDDM 下 used_memory 全 N/A（进程级测量受限） |

## 二、诊断结论

1. **最大浪费点 = 启动基线与空载的差值 ~8.5G**：backend 启动即预载 bge 嵌入（CUDA）+ warmup 链条，即使用户全天只用对话也占着。两级回收（60s/300s）理论可回收，但 embedding 是否纳入回收范围待审计。
2. **CUDA context 碎片**：src/ComfyUI/H3/vLLM 四进程各有独立 context（~300-500MB/个），Windows WDDM 下进程级测量 N/A，无法精确定位——合并进程=架构大改，不可行。
3. **双栈分工已有效**：管理员 default=4b → 走 legacy diffusers（44s/张），comfy 9b 仅质量路线按需——选型语义已生效（撤回前轮失配推断）。

## 三、方案（四段制）

### 改动清单
- **A1 embedding 延迟加载**：bge 从「启动即 CUDA 预载」改为「首次知识检索时装载」+ 空闲 60s 后自动卸载（复用两级回收机制）——基线预期 10.8G→~5G，腾出 ~6G 给生成链
- **A2 回收范围审计**：确认 embedding/aux 类模型在 shallow_reclaim（60s）覆盖范围内；不在则纳入
- **A3 画像常驻化**：每 30s 采样 GPU 总占用+进程计数落 events，供后续自动调参与 S8 观察期数据积累
- **不做什么**：跨进程 CUDA 合并（不成熟）、H3 进一步量化（高风险）、vLLM 睡眠（上游 bug）

### 影响面
- 知识检索首次响应多一次嵌入装载等待（~10-20s，之后热）；RAG 链路首次查询延迟增大
- 生成链显存空间 +6G：H3 720p 档成功率提升、comfy+PuLID 大分辨率裕度增加

### 验证方法
- 冷启动→基线实测（预期 ≤5G）；知识检索实弹→bge 装载→60s 后卸载→基线回落
- 关键帧生成峰值对比（释放出的 6G 应降低 OOM 率）
- 一键体检通过+RAG 金标 20 例回归

### 风险与回退
- config 开关 `vector.lazy_load: false` 一键还原；金标 20 例回归保障检索质量
- 首查延迟为可感知退化——产品层面权衡：显存收益 > 首查延迟（知识检索非高频首屏操作）

### 代价
- 0.5~1 人日（含实弹验证）；零下载零新依赖
