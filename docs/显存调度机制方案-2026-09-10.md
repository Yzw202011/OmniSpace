## 一、背景：为什么现有机制「不符合了」

### 1.1 现状全景：7 套判断、4 本账、0 个总协调者

当前对「显存够不够 / 该杀谁 / 谁先跑」的裁决分散在至少 7 处，各写各的逻辑：

| # | 机制 | 位置 | 判断方式 |
|---|------|------|----------|
| 1 | 模型装载分配 + 驱逐 | `model_manager/__init__.py:646-704`（allocate_memory） | 逻辑预留账 `_reserved_vram_gb` + 台账 `_loaded` + NVML 读数 |
| 2 | vLLM 准入等待 | `engines/vllm_service.py:416-459`（_vram_admission_wait） | 设备级 mem_get_info，60s×2s 轮询 |
| 3 | vLLM 自适应让档 | `inference/backends/vllm_backend.py:112-153` | floor = 权重 + 4.2（开销 3.4 + KV 0.8），不足降 util |
| 4 | 绘画自卸链 | `inference/paint_engine.py:532-569`（_try_free_vram） | 自带「卸对话→循环驱逐→直接卸对话引擎」 |
| 5 | 危急线再卸一轮 | `services/resource_guard.py:196-241`（_shed_vram） | NVML ≥90% 触发，逐卸空闲模型 |
| 6 | 按卡记账器 | `engines/vram_manager.py:92-143` | per-device 记账——**但没有任何决策方消费它**，只出遥测 |
| 7 | 队列准入 | `image_queue.py:371-394` / `video_queue.py:316-337` | **只等锁、等温度，不看显存** |

**四本账互不同步**：① `_loaded` 台账（model_manager）② `_reserved_vram_gb` 逻辑预留 ③ `vram_manager._device_allocated_mb` ④ NVML/torch 物理读数。除 1↔2 有孤儿对账钩子（`model_manager:687-695`）外彼此零同步。

### 1.2 七个具体病灶（各有实证）

1. **9B 主力常态装不下，静默降级成常态**：16GB 卡白天常态空闲 ~13.4GB（`docs/架构升级计划-2026-09-05.md:43`），qwen35-9b-w4a16 装载需 14.9GB（`docs/底层架构升级方案-2026-09-08.md:348`）——默认模型在本机「永远装不下」，只能降级 8B/4B。而 **GGUF 9B Q4_K_M 只需 5.7GB、114 tok/s、质量碾压 4B**（POC 已实证，资产在 `models/qwen35-9b-gguf-q4km` + `runtime/llama-poc`），却未纳入任何调度/路由层。
2. **80% 预警档实际无效**：0.80 档唯一动作 CPU_ASSIST→migrate_to_cpu，在功能锁持有时整体跳过（`scheduler/dispatcher.py:125`）——**恰恰是生成期显存越过 80% 时什么都不做**，0.80~0.90 之间是空调区，只剩 90% 守卫兜底。
3. **vLLM 生命周期有 4 个编排者**：image_queue（10s 去抖唤醒 `image_queue.py:443-479`）、video_queue（**排空立即唤醒，无去抖** `video_queue.py:209-212`）、关键帧重抽（`api/manga/keyframe.py:2274-2295`）、一致性守卫（`keyframe.py:1965-1995`）各自 sleep/wake 同一个 vLLM 子进程，时序交错全靠 feature_lock 间接串行——历史「唤醒撞锁」事故只修了 image_queue 一处。
4. **两条队列 + 直连端点三路抢锁，无全局排序**：paint 队列与 video 队列互不感知，谁 1s 轮询先抢到锁谁先跑；排队期间不做任何显存预判。
5. **云端任务零感知**：cloud:True 任务不取锁、不进任何账（`cloud_provider_service.py` 本身纯连接管理）——云任务跑着的时候，系统判定「全空闲」，空闲回收/预加载可能误触发。
6. **多卡地基铺了、消费侧全单卡假设**：批1 多卡地基（`engines/gpu_domains.py`，2026-09-05 入库）已把功能→卡分配做成单源，但 monitor 遥测硬编码 0 号卡（`scheduler/monitor.py:103`）、model_manager 显存判定同样只看 0 号卡（`model_manager/__init__.py:340`）——**1 号卡的温度/占用在调度视野里不存在**。
7. **阈值治理半途**：RAM 侧 4 常量已收敛到 `vram_policy.py`（V9-尾款①，2026-09-09），GPU 侧全部数值（util 0.85/0.87/0.92、floor +4.2/+1.3、×0.98、训练 10GB 线、ComfyUI 300s、对话 900s）仍散落 6+ 文件。另有陈年失真：`release_for_module` 杀 vLLM 后台账回写硬编码旧模型名 `"qwen3-vl-8b-awq(vllm)"`（`model_manager/__init__.py:1283`，默认模型已换代 9B）。

### 1.3 供需错配总表（调度设计的关键事实）

16GB 开发机（5070 Ti）运行态空闲常态 **13.4GB**（桌面驻留 ~2GB + bge 1.3GB）；12GB 基线机（3060）无 FP8 能力。

| 场景 | 模型 | 显存需求（实证） | 16GB 常态 | 12GB |
|------|------|------------------|-----------|------|
| 对话主力 | qwen35-9b-w4a16 | **14.9GB**（权重 10.95+MTP 0.49+KV+激活） | ❌ 装不下→降级 | ❌ |
| 对话 GGUF 档 | qwen35-9b-gguf-q4km | **5.7GB** / 114 tok/s（POC 实证） | ✅ 可共存 | ✅ **唯一 9B 解** |
| 对话次选 | qwen3-vl-8b-awq | 峰值 **14.8GB**（vllm_bench 实测） | 🔶 需让渡 | ❌ |
| 对话兜底 | qwen3-vl-4b | 9.0GB | ✅ | 🔶 独占勉强 |
| 关键帧/绘画 | flux2-klein-9b Q6_K | 实测峰值 **14.1~15.1GB** | 🔶 独占（vLLM 必让渡） | 🔶 Q4 降档 |
| 新画笔(B2) | qwen-edit-2511 | 峰值/稳态 **15.7/11.4GB** | 🔶 独占 | ❌ |
| 高精绘画 | qwen-image-2512 流式 | GPU 仅 **~0.5GB**，RAM 需 22GB | ✅（RAM 是主约束） | ✅（RAM 够时） |
| 漫剧视频 | minimax-h3 | 峰值 ≈ 7.4+0.0255×帧数 GB（243 帧=15.2 擦线） | 🔶 ≤10s 短段 | 🔶 5s 段 10.6GB |
| 备选视频 | wan22-ti2v-5b | split 常驻 ~13.3GB | 🔶 独占 | 🔶 int8 5.2GB |

**结论**：本项目的显存现实是「一卡不容二虎 + 一个 5.7GB 的轻量例外」。调度机制的使命不是把多个大模型塞进一张卡，而是：**算清账、让位有序、降级可见、排队有全局次序、轻量档充分利用空隙**。

## 二、设计目标与原则

1. **一个总管**：所有「够不够 / 让谁走 / 谁先进」收敛到一个显存协调器（GPU Budget Coordinator），其余组件只「申请」与「归还」。
2. **一本账**：物理读数为最终真值，台账为解释层，两者差值（外部占用）作为对账依据；孤儿/幽灵占用自动收账。
3. **策略与机制分离**：所有阈值/档位/让位阶梯进 `vram_policy.py` 单源（RAM 侧已先行，GPU 侧跟进），代码里消灭魔法数；对拍测试锁值。
4. **降级必须可见**：换档（9B→GGUF/8B/4B）复用既有 `model_fallback` 广播与「（自动降级）」警示，绝不静默。
5. **失败必须诚实**：装不下就明确告知 + 出路指引（云档提示 / 排队位次 / 空闲窗口预估），不空转重试。
6. **渐进落地**：每批独立可回退；协调器任何路径异常时降级为「直接看物理读数」——最坏退回现状行为，不会更糟。

## 三、新机制设计（六个组件）

**总图（大白话版）**：现在的显存像一间 16 平米的房间，7 个管家各管各的、4 本账对不上。新机制 = 一个房间总管（协调器）+ 一本总账（对账）+ 一张价目表（策略单源）+ 一个排队窗口（准入编排）+ 一份床位表（生命周期状态机）+ 一块「房客名单」公示牌（忙碌登记，云任务也上榜）。

### 3.1 组件一：统一账本 `gpu_budget.py`（新文件）

唯一的显存状态真源，提供：

```python
@dataclass(frozen=True)
class BudgetSnapshot:          # 每卡一份
    device: int
    total_gb: float
    free_gb: float             # torch.cuda.mem_get_info(该卡) 物理读数
    ledger_gb: float           # 台账在账模型合计（合并 _loaded，vram_manager 并入）
    reserved_gb: float         # 已批准未落地的逻辑预留合计
    external_gb: float         # physical_used − 台账 − 基线 ≈ 账外占用（对账依据）

def snapshot(device: int | None = None) -> BudgetSnapshot      # 全卡枚举，不再硬编码 0
def reconcile(snapshot) -> None   # external 异常持续 → 触发孤儿收账（vllm_service.reap_orphans 等）
```

- **多卡修复一并完成**：monitor（`monitor.py:103`）与 model_manager（`__init__.py:340`）的 `nvmlDeviceGetHandleByIndex(0)` 改为按目标卡枚举——这是多卡地基（gpu_domains）真正可用的前提。
- vram_manager 不再独立记账：其 `_device_allocated_mb` 并入本账（保留 get_usage 遥测兼容层）。

### 3.3 组件三：准入编排（request / release）——所有重型任务的唯一入口

```python
class Verdict(Enum): GRANTED / WAIT / DOWNGRADE / DENY

def request(feature: str, need_gb: float, *, device: int | None = None,
            wait_s: float = 60, allow_yield: bool = True) -> RequestResult
def release(handle) -> None
```

决策序列（每步之间重新 snapshot）：

1. **对账**：external_gb 异常且持续 → 先收孤儿（复用 `vllm_service.reap_orphans:1067-1081` 等既有能力）；
2. **直接放行**：free − reserved ≥ need → GRANTED + 记逻辑预留；
3. **让位阶梯**（allow_yield 时，从零成本到高成本逐级执行、逐级复测）：
   - **L0 零成本**：取消进行中的预热（`/models/warmup` fire-and-forget 可中断化）、暂停后台学习、延迟非关键写入；
   - **L1 小模型回收**：embed/aux/voice（等同现行 60s 表层回收的主动版）；
   - **L2 重量级让渡**：vLLM 让渡（Windows 语义=停子进程，让出 ~12-14.8GB，成本 157s 冷启）/ ComfyUI `/free` 卸权重保进程——**只由协调器执行，其他组件一律申请**；
   - **L3 拒绝并指路**：返回 DENY + 出路（云端槽位提示 / 更小档位提示 / 排队）。
4. **可降档则建议降档**（DOWNGRADE + 候选，见 3.5），交调用方带可见性执行；
5. **否则 WAIT**：返回排队位次与预计触发条件（复用现有队列广播）。

**接入面**（替换各自手搓判断，语义不变或收紧）：
- image_queue / video_queue 的 `_wait_admission`（锁与温度等待保留，显存预判新增）；
- vllm_service `_vram_admission_wait` 与 vllm_backend 让档计算（变薄封装，调用协调器）；
- paint_engine `_try_free_vram`（整个删除，收敛为一次 request）；
- resource_guard `_shed_vram`（保留为危急线兜底，但驱逐判定语言统一，见 3.4）；
- 训练 10GB 闸、`/models/load`、`/models/switch`。

**驱逐语言统一**（消灭两套并存）：现行 `evict_lowest_priority`（只看类别优先级，`model_manager:746-761`）与 `_FEATURE_KEEP_CATEGORIES`（看锁，`:80-85`）合并为一条规则——**先排除持锁活跃功能所需类别，再按优先级驱逐**。修复「翻译进场与绘画互拆」的双路径（`prompt_translator.py:90-105` + `paint_engine.py:532-569`）。

### 3.4 组件四：生命周期状态机 + 单一编排者

- **vLLM**：`UNLOADED → BOOTING → READY → YIELDING(让渡中) → UNLOADING`（对话引擎已有近似状态机 `dialog_engine.py:1840-1875`，对齐术语）；sleep_for_paint / wake_from_paint（`vllm_service.py:295-414`）收归协调器内部方法，**4 个编排点（image_queue / video_queue / keyframe 重抽 / 一致性守卫）改为申请-归还**；
- **唤醒去抖统一**：video_queue 补上与 image_queue 相同的 10s 去抖（`video_queue.py:209-212` 与 `image_queue.py:443-479` 对齐），规则进策略单源；
- **ComfyUI 空闲感知**：空闲计时增加两个豁免——功能锁持有中不计时、任一队列还有本地任务时不计时（`comfy_proc.py:371-396` 的 `_idle_loop`），避免任务间隙 >300s 被「空闲关闭」后下镜 40s 冷启动；
- **80% 档修复**（消灭空调区）：warning 档动作表拆两态——生成期（锁持有）：只做零成本动作（停预热 / 阻新准入）+ 日志升级；非生成期：维持现 CPU_ASSIST 行为。90/95 档维持现状但动作与阈值顺序理顺（95 档不再比 90 档更迟钝）。

### 3.5 组件五：档位路由整合（GGUF 档入列，含 D2 决策）

对话档位表进 `vram_policy.py`（数值均有实证）：

```python
DIALOG_TIERS = [
    Tier(model="qwen35-9b-w4a16",    vram_gb=14.9, mode="vllm",  note="独占档"),
    Tier(model="qwen35-9b-gguf-q4km", vram_gb=5.7,  mode="llama", note="共存档(POC实证)"),
    Tier(model="qwen3-vl-8b-awq",     vram_gb=14.8, mode="vllm",  note="次选"),
    Tier(model="qwen3-vl-4b",         vram_gb=9.0,  mode="inproc", note="兜底"),
]
```

- **选档逻辑前移**：不再「先试 9B → 装载失败 → 静默降级」，而是协调器在准入时按当前空闲直接判定可装档位，**换档全程走既有 `model_fallback` 广播 + 气泡「（自动降级）」警示**（降级可见性已落地，复用不重造）；
- **GGUF 档集成**（若 D2 拍板）：新增 llama-server 子进程管理（对齐 vllm_service 的孤儿收账/Job Object/绑卡模式，资产 `runtime/llama-poc` 已就位）；manifest 补登记 `qwen35-9b-gguf-q4km`（顺手补 `qwen-edit-2511` 的未登记项）；
- 12GB 基线机：GGUF 档成为 9B 唯一解，档位表按 `HARDWARE_TIER_TABLE` 档位裁剪。

### 3.6 组件六：忙碌登记簿（云任务上榜）

- 协调器维护 `busy_registry: {feature, kind: local|cloud, since}`；
- 云端任务在 6 个提交点（draw.py:798-826 / keyframe / comic_asset / video.py / storyboard / novel_service）入队时登记、完成注销——**不取本地锁（现状保留），但让「系统空闲」判定看见它**；
- 消费方：空闲回收（`scheduler/__init__.py:225-306`）、对话 900s 看门狗（`dialog_engine.py:1877-1924`）、ALL_IDLE 预加载、ComfyUI 空闲计时。
