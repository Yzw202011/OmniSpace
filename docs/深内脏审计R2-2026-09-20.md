## ① N+1 查询反模式 —— 🔴 46 处

**循环体内 DB 调用**（每次迭代一次查询=数据库被打 N 次）：

| 重灾区 | 处数 | 典型 |
|---|---|---|
| system.py | 7 | 项目恢复循环逐表 insert（1436~1474 行四连） |
| comic_asset/storyboard | 10 | 批量删除/查询循环逐行 |
| novel_service | 4 | 章节删除循环 |
| dialog/draw/learn | 5 | 批量删除逐条 `db.delete()` |

**典型病灶**：`api/novel.py:171` `for table in [...]: db.delete(table, "project_id=?", (pid,))` ——6 张表循环删=6 次 DB 往返，应用 `execute_in_transaction` 一次搞定。

**定级**：🔴 性能地雷——数据量小无感，但删一个 50 章小说项目=300 次 DB 往返。

## ④ 响应模式不一致 —— 🟡

同族「列表」端点 data 形状各异：
- learn tasks/models：`{items, total}` ✓（分页标准形态）
- logs modules：`{modules}` ——直接裸数组包一个 key
- dialog sessions（批量删）：`{deleted, deleted_ids, missing_ids}` ——与列表端点完全不同的域
- novel chapters（批量生成）：`{tasks, queued, skipped_completed}` ——又一种

**本质**：无「列表端点标准 data 契约」（分页/排序/总数字段命名未归一）。
