## 一、一句话设计

把「失败出路、日志打点、自动加载、一键体检」四件每个功能都该有的事，从**每个端点手写**改成**中间件/依赖层自带**——新功能就算一行防护都不写，也自动获得底线保障；写得好的可以覆盖得更细。

生活比喻：与其每次装修都提醒工人「记得装灭火器」（A 规矩）或验收时拿清单查（B 闸门），不如把**消防喷淋接进水管总闸**——通水就自带（C 内建）。

## 三、四批设计（每批独立落地、独立验收、可随时叫停）

### 批1 错误出路默认化（吸收 L2 根件）——约 0.5 天

- `error_handler.py` 新增 `SUGGESTION_DEFAULTS: dict[语义码, 出路文案]`：给全部语义码配默认出路（如 `MODEL_NOT_LOADED`→「直接重试即可，系统会自动加载模型；若反复失败，到模型管理页检查」）；`error()` 在调用方未传 suggestion 时自动补。
- 未登记码/未知码兜底一句通用出路：「请稍后重试；若反复出现，设置页→导出诊断包」。
- 前端配套：核对通用错误提示位（toast/横幅）把 suggestion 一并展示（现状仅 2 组件渲染，🔶 覆盖面实施时逐处核对）。
- **效果**：从此任何错误（含未来新功能只要用了语义码）自动带出路，「裸报错」灭绝。

### 批2 API 事件日志自动兜底——约 0.5-1 天

- 新增 `middleware/event_log_auto.py`（纯 ASGI，仿 RequestContextMiddleware 模式），main.py 挂载一行。
- **记录范围**（防刷屏，阈值进 config.yaml 可调）：①变更类请求（POST/PUT/DELETE/PATCH，复用 `_ACTIVITY_METHODS` 语义）②任何失败信封 ③耗时 >3s 的慢请求。GET 轮询不记。
- 每行自动 log_event：module=按路由前缀映射（/draw→paint、/manga/keyframe→manga…，对齐前端 MODULE_NAMES 中文名表补条目）、level=success/error、duration_ms、friendly=模板生成（「绘画·图片生成 完成，用时 12.3 秒」/「失败：模型未加载——出路：…」）。
- 可选精修：`EVENT_LABELS` 注册表让端点用一行登记更准的中文动作名；**忘了登记也有通用模板兜底**（这正是 C 的意义）。
- 与业务内 log_event 的关系：互补不重复——业务打点记「发生了什么」（模型加载/降级），本层记「这次接口成没成」。
- **效果**：新端点上线当天就在日志页时间线可见，「日志不联动」灭绝。

### 批3 模型自动加载依赖化——约 1 天

- 新增 `backend/api/deps.py`：`require_engine(engine_key)` FastAPI 依赖工厂——端点声明 `Depends(require_engine("paint"))` 即自带：is_ready 检查 → 未就绪自动 `run_blocking(engine.ensure_loaded)` → 进度经现有预热/WS 通道广播（🔶 通道复用可行性试点时实证）。
- 试点改造 2 个端点（荐：绘画生成 + 漫剧关键帧——都是 09-02 漏网同型地）；跑通后写入开发惯例，新端点一行声明即自带。
- 已知雷（写进实施守卫）：VRAM 协商时序（历史事故「翻译先于 ensure_loaded」）→ 试点挑无翻译前驱的端点；ensure_loaded 是数秒级阻塞必须走 run_blocking（models.py:1169 先例）。
- **效果**：「模型未加载让用户再点一次」从制度上不可能——这就是 ux-model-load-auto 铁律的架构化。

### 批4 一键体检与修复（吸收 L1）——约 1-2 天

- 后端 `GET /system/health-check`：只读体检（GPU/显存余量、孤儿引擎进程、模型登记 vs 磁盘对账、磁盘空间、日志保留、队列状态、激活状态），结果大白话 + log_event 落档。
- 修复动作**白名单制**（只做零数据风险的）：清过期日志、重建缺失目录、清「确认孤儿」的引擎进程（**守卫：绝不碰后端本体，对齐 §16.4 走正规退出链的既有先例**）；其余项仅报告 + 给出路。
- 前端设置页「体检与修复」卡片：一个按钮，出报告，可修项一键修。
- **效果**：普通用户「不专业也不怕」——出问题自己先体检，而不是面对一堆技术日志。

## 四、四段制（§16.1）

1. **改动清单**：批1=error_handler.py（+默认出路表与兜底逻辑）+前端错误提示位核对；批2=新增 middleware/event_log_auto.py + main.py 挂载一行 + 前端 MODULE_NAMES 补名；批3=新增 api/deps.py + 试点端点 2 处改 Depends；批4=system.py 体检端点 + 设置页卡片。**不动任何业务逻辑语义。**
2. **影响面**：批1=所有错误响应多出 suggestion 字段内容（前端已全局解析，纯增量）；批2=变更类请求每次多写一行 jsonl（本地单用户日增约百行级，30 天保留，体积可忽略 🔶 量级估算）；批3=试点端点未加载时由「报错」变「自动加载后成功」（行为升级，正是产品铁律方向）；批4=纯新增只读端点 + UI 入口。
3. **验证方法**（§16.2 实弹，每批过完才进下批）：批1=单测（全语义码 error() 必带出路）+ curl 实弹无 suggestion 错误验信封；批2=单测（假 app：POST 出行/GET 不出/失败 level=error）+ 真浏览器点一次生成→日志页时间线出现大白话条目；批3=E2E（卸载引擎态直接调试点端点→观察到自动加载+进度可见→请求成功）；批4=实弹（点体检出报告→造一个可修项如过期日志→一键修→复验转绿）。
4. **风险与回退**：批1=默认文案与个别错误语义不匹配 → 文案保守通用+高危码人工抽查；回退=删表一行。批2=刷屏/性能 → 范围三条件+阈值可配；回退=main.py 卸载一行。批3=VRAM 协商时序雷 → 试点挑无翻译前驱端点+单独 E2E；回退=试点端点还原旧写法。批4=修复误伤 → 白名单只含零数据风险动作；回退=隐藏入口。**四批均为纯增量，全退也无残留。**
