## 1.2 六大核心模块详解

### 1.2.1 AI对话模块 (OmniChat)

【技术选型】
  - 推理模型：Qwen3-VL-8B-Instruct / Qwen3-VL-4B-Instruct / Qwen3-VL-2B-Instruct
  - 推理后端：vLLM (高性能大模型推理库)
  - 上下文长度：最大 8K tokens
  - 量化方案：支持 fp16 / int8 / int4 动态切换
  - 流式输出：SSE (Server-Sent Events)

【功能清单】
  - 多模态对话：支持文本+图像输入，流式文本输出
  - 剧本润色：基于影视行业知识库的专业润色
  - 分镜描述生成：输入剧情自动生成结构化分镜描述
  - Agent 工具调用：基于 Function Calling 协议，支持浏览器搜索、文件操作等
  - 上下文记忆：多轮对话记忆，支持会话持久化
  - RAG 增强：每次对话前自动检索 ChromaDB Top-5 知识片段
  - 被动补全：检测到知识缺口时自动触发联网学习
  - 流式输出：SSE 推送，打字机效果

【输入输出】
  - 输入：文本 (Markdown) / 图像 (PNG/JPG/WebP) / 混合多模态
  - 输出：文本 (Markdown) / JSON / 结构化数据

【依赖关系】
  - 强依赖 ModelManager 进行模型权重加载与显存管理
  - 依赖 LearningEngine 获取 RAG 知识注入
  - 依赖 KnowledgeInjectionService 进行检索增强
  - 与 OmniDraw 兼容（共享显存池）
  - 与 OmniComic 兼容（Agent 驱动）
  - 与 OmniLearn 互斥（CPU 竞争）
  - 与 VideoStyle 互斥（GPU 计算冲突）

【实现原理】
  1. 用户输入经前端捕获，通过 HTTP POST /api/v1/chat/send 发送
  2. FastAPI 路由层完成 Pydantic v2 参数校验
  3. ChatService.chat_stream() 进行 RAG 检索（ChromaDB Top-5, <100ms）
  4. BGE-large-zh 向量化查询，ChromaDB 相似度检索，过滤 score<0.5 结果
  5. 组装上下文：系统Prompt + 检索知识 + 历史对话 + 用户输入
  6. 根据 GPU 显存自动选择模型规模（8B/4B/2B）
  7. PyTorch 2.8 流式推理，yield token 逐字输出
  8. 可选被动补全：检测不确定性标记 -> 提取关键词 -> 快速搜索 -> 补充推理
  9. 记录对话历史至 SQLite，触发行为学习记录（后台异步）
  10. SSE 流式返回 token 至前端，打字机渲染


### 1.2.2 AI绘画模块 (OmniDraw)

【技术选型】
  - 核心模型：FLUX.1-dev (FP8量化) / Kolors 2.1 / SDXL-Base-1.0
  - 控制网络：ControlNet-OpenPose (姿态控制)
  - 风格迁移：IP-Adapter-Plus (多图权重混合)
  - 推理框架：ComfyUI-Core 嵌入式，节点化工作流
  - 量化方案：FP8 / FP16 / INT8 动态切换

【功能清单】
  - 文生图 (Text-to-Image)：支持中文 Prompt，1024x1024 及以上分辨率
  - 图生图 (Image-to-Image)：参考图引导生成，可调节相似度
  - ControlNet 姿态控制：OpenPose 骨骼提取 + 姿态约束生成
  - IP-Adapter 风格迁移：支持多图权重混合，风格相似度 SSIM>0.85
  - 局部重绘 (Inpainting)：遮罩区域智能修复
  - 超分辨率 (Upscale)：Real-ESRGAN 4x 放大
  - Prompt 优化：调用 OmniChat 进行 Prompt 扩写增强
  - 批量生成：队列式批量图片生成

【输入输出】
  - 输入：Prompt (文本) / 参考图 (PNG/JPG) / ControlMap (骨骼图)
  - 输出：高分辨率图像 (PNG/EXR) / Base64 / 文件路径

【依赖关系】
  - 强依赖 ModelManager 进行模型权重加载
  - 依赖 OmniChat 进行 Prompt 扩写优化
  - 依赖 LearningEngine 获取风格知识
  - 与 OmniChat 兼容（共享显存池）
  - 与 OmniComic 强依赖关系（提供关键帧）
  - 与 OmniLearn 互斥（显存竞争）
  - 与 VideoStyle 互斥（GPU 计算冲突）

【实现原理】
  1. 用户通过前端参数面板设置 Prompt、Negative Prompt、模型、步数、CFG、尺寸等
  2. POST /api/v1/paint/generate 发送请求
  3. PaintService 解析参数，调用 OmniChat 进行 Prompt 扩写（可选）
  4. 根据硬件等级选择模型：RTX 5090/4090 -> FLUX.1-dev；RTX 4070Ti -> Kolors 2.1
  5. ComfyUI-Core 节点化工作流：CLIP Encode -> UNet Denoise -> VAE Decode
  6. ControlNet 分支：OpenPose 提取 -> ControlNet 注入 UNet
  7. IP-Adapter 分支：参考图 CLIP Embedding -> Cross-Attention 注入
  8. FP8 量化推理保证显存安全
  9. 生成进度通过 WebSocket 实时推送至前端
  10. 完成生成 -> 保存 PNG -> 更新历史画廊 -> 通知用户

【技术选型】
  - 分镜引擎：自定义 DSL 分镜表解析器
  - 3D导演台：Three.js r170 (WebGL in-browser rendering)
  - 视频生成：LTX-Video-2B / Wan2.1-14B / CogVideoX-5B

    与前端渲染管线深度集成

【功能清单】
  - 分镜脚本解析：自定义 DSL 语法，解析成功率 100%
  - 3D 资产编排：支持 USDZ/glTF 格式，10万面资产加载 <3s
  - 视频片段生成：LTX-2 720p/30fps，5s 视频 <60s 生成
  - 多镜头一致性控制：闪烁率 <1%
  - 视频后处理：FFmpeg 裁剪/拼接/AV1 编码
  - 批量分镜生成：队列式批量处理

【输入输出】
  - 输入：结构化剧本 / 3D场景描述 / 参考图
  - 输出：视频序列 (MP4) / 分镜图 (PNG) / 3D 场景截图

【依赖关系】
  - 强依赖 OmniDraw 提供关键帧
  - 依赖 VideoStyleEngine 进行风格统一
  - 依赖 LearningEngine 获取分镜/场景知识
  - 与 OmniChat 兼容（Agent 驱动）
  - 与 OmniLearn 互斥（显存+CPU 竞争）
  - 与 VideoStyle 互斥（GPU 计算冲突）

【实现原理】
  1. 用户上传结构化剧本或手动编辑分镜表
  2. DSL 解析器将剧本拆分为分镜序列（镜头/角度/运动/角色/表情/动作/时长/转场）
  3. 3D 导演台：Three.js r170 基于 WebGL 在浏览器内完成 3D 场景渲染
     - 无需独立渲染进程，与前端渲染管线深度集成
     - 支持对象放置/拖拽/旋转/缩放/相机控制
  4. 关键帧生成：调用 OmniDraw 生成每个分镜的关键帧
  5. 视频生成：LTX-2 / Wan2.1 / CogVideoX 将关键帧扩展为视频片段
  6. 多镜头一致性：光流法 + Latent 约束保证帧间平滑过渡
  7. FFmpeg 7.x 后处理：裁剪/拼接/转码/AV1编码
  8. 导出 MP4：完整视频序列 + 分镜表

【输入输出】

  - 输出：模型句柄 / 显存映射

  3. 显存不足时：检查可卸载模型 -> 卸载最低优先级模型 -> 加载新模型

  6. ML 预测预加载：XGBoost 预测 -> 概率>0.7 -> 异步加载 -> 用户切换即时可用

## 1.3 五大智能引擎详解

### 1.3.1 LTX-2 LoRA 微调引擎

【技术原理】
  - 基于 LTX-2 Diffusion Transformer 的 Low-Rank Adaptation 微调
  - 冻结预训练权重，仅训练低秩分解矩阵 (A 和 B)
  - QLoRA 4bit 量化 + 梯度检查点技术，支持显存分块训练
  - 24GB 显存可训练 720p LoRA
  - peft 库 + bitsandbytes 4-bit 量化实现

【触发条件】
  - 用户在 VideoStyle 或 OmniLearn 提交训练任务
  - 训练数据累积 >= 100条自动触发
  - 用户设定时间到达（默认每周一次）
  - 用户手动触发

【执行流程】
  数据预处理 -> 基座模型加载(Qwen3-14B/ChatGLM-4-9B) -> QLoRA 4bit 量化 ->
  显存分配 -> 梯度累积 -> 训练循环(Epochs=3, LR=2e-5, rank=16, alpha=32) ->
  Checkpoint 保存 -> 质量评估(困惑度+生成质量+领域相关性) ->
  通过则注册新版本 -> 通知用户；未通过则保留旧版

【量化指标】
  - 训练 Loss 收敛且无灾难性遗忘
  - 风格一致性 > 0.9
  - 24GB 显存可训练 720p LoRA
  - v2.3.1 加速：Flash Attention-2 + 8bit AdamW，训练时间减少 >30%


### 1.3.2 模型预加载 ML 预测引擎

【技术原理】
  - XGBoost 时序预测模型，基于历史操作序列预测下一模型
  - 特征窗口：50步历史操作序列
  - 特征工程：当前功能、操作时间（小时/分钟）、操作序列（最近10步）、
    历史功能切换模式、项目上下文
  - 模型大小：~50MB，常驻内存

【触发条件】
  - 用户完成当前操作后
  - 系统空闲 >500ms
  - 功能切换事件

【执行流程】
  用户操作事件流 -> 特征提取 -> XGBoost 推理 (<50ms) ->
  预测下一个功能 + 概率 -> 概率 > 0.7 -> 触发预加载 ->
  检查 GPU 空闲显存 -> 异步加载模型到 GPU -> 更新缓存状态 ->
  用户切换时 -> 即时可用 (0等待)

【量化指标】
  - 预测准确率 > 85% (v2.3.1 优化后)
  - 推理延迟 < 50ms
  - 模型大小 ~50MB


### 1.3.3 协同调度历史学习引擎

【技术原理】
  - 强化学习 (PPO - Proximal Policy Optimization) 优化资源分配策略
  - 状态空间：GPU显存/CPU/内存/当前活跃功能/任务队列
  - 动作空间：模型加载/卸载/精度调整/任务优先级调整
  - 奖励函数：用户等待时间负奖励 + 资源利用率正奖励 + OOM 大额负奖励

【触发条件】
  - 系统资源冲突
  - 任务完成反馈
  - 定期分析优化（每小时）

【执行流程】
  状态观测 -> 策略网络推理 -> 动作执行 -> 奖励计算 -> 策略更新 ->
  记录调度决策与效果 -> 自适应调整预加载阈值

【量化指标】
  - 调度效率提升 > 20%
  - 资源冲突率 < 1%


### 1.3.4 AV1 硬件编码引擎

【技术原理】
  - 硬件加速 API 封装：NVENC (NVIDIA) / AMF (AMD)
  - 软编降级：SVT-AV1 (Scalable Video Technology for AV1)
  - 码率控制：CRF 23 / VBR 自适应
  - 编码参数：preset 6, keyint 240, AAC 256kbps 音频

【触发条件】
  - 视频生成/导出任务启动
  - 用户手动触发视频导出

【执行流程】
  视频导出请求 -> 硬件探测 ->
  RTX 50系 -> NVENC AV1 硬编（速度最快, >120fps）->
  RTX 30/40系 -> NVENC H.264/H.265 硬编（>80fps）->
  AMD RX 6000+ -> SVT-AV1 软编（多线程）->
  纯CPU -> SVT-AV1 软编（低速）->
  码率控制 -> 帧级编码 -> 封装 -> 进度回调 -> 完成通知 ->
  失败 -> 自动降级 (AV1 -> H.264)

【量化指标】
  - RTX 50系 NVENC AV1：编码速度 >120fps
  - RTX 30/40系 NVENC：编码速度 >80fps
  - SVT-AV1 软编：CPU占用 <80%，画质达标


### 1.3.5 自主学习引擎 [v2.3新增]

【技术原理】
  - RAG (Retrieval-Augmented Generation)：ChromaDB 向量检索 + BGE-large-zh 嵌入
  - Agent 决策树：ReAct 模式 (Reasoning + Acting)，目标驱动自主浏览
  - 增量学习闭环：知识发现 -> 入库 -> 触发微调/更新 RAG 索引
  - 好奇驱动：PPL (Perplexity) 驱动的好奇心探索 + 知识图谱覆盖率奖励
  - 双层反哺：RAG 即时注入 (毫秒级) + LoRA 深度融入 (分钟级)

【触发条件】
  - 用户授权学习
  - 系统检测到新知识源（网页/文档/操作行为）
  - 对话中遇到知识缺口（被动补全）
  - 定时触发（RSS 订阅）

【执行流程】
  内容抓取 -> 知识抽取 -> 质量评估 -> 去重 (SimHash) ->
  ChromaDB 入库 -> RAG 索引即时可用 ->
  训练数据累积 >= 100条 -> 触发 LoRA 微调 -> 全功能使用

【量化指标】
  - 创作功能延迟增加 < 5%
  - 知识提取速度 > 5个知识点/页
  - 检索延迟 < 100ms
  - 关键信息召回率 > 90%

## 4.1 性能自适应调整

### 4.1.1 GPU显存监控与自适应降参策略

系统需实现毫秒级显存监控，根据当前占用率动态调整模型推理参数，防止OOM崩溃。

+-------------------+-------------+-----------------------------+-----------------------------------+
| 显存使用率阈值     | 状态定义     | 精度降级策略                 | 模型卸载策略                       |
+-------------------+-------------+-----------------------------+-----------------------------------+
| < 70%             | 安全区       | 维持 fp32/bf16               | 全量驻留显存                       |
| 70% - 85%         | 警戒区       | 降级至 fp16                  | 保持全量驻留，开启显存碎片整理     |
| 85% - 95%         | 危险区       | 降级至 bf16/int8             | 卸载非活跃LoRA权重至内存           |
| > 95%             | 溢出区       | 强制 int8 量化推理           | 卸载基础模型至内存，启用CPU Offload|
+-------------------+-------------+-----------------------------+-----------------------------------+

### 4.1.2 GPU利用率自适应

+-----------------------------+---------------------------------------------+
| 检测条件                     | 调整动作                                     |
+-----------------------------+---------------------------------------------+
| GPU 显存 > 90%               | 降低模型精度 / 卸载非活跃模型                |
| GPU 利用率 > 95% 持续 10s    | 降低生成质量参数                             |
| GPU 温度 > 85度C             | 触发降频，Batch Size 减半                    |
| GPU 温度 > 90度C             | 强制暂停生成任务并弹出UI警告                 |
| 连续3次高温降频              | 当前会话内锁定最大GPU利用率至80%             |
+-----------------------------+---------------------------------------------+

### 4.1.3 CPU与内存自适应

+-----------------------------+---------------------------------------------+
| 检测条件                     | 调整动作                                     |
+-----------------------------+---------------------------------------------+
| CPU > 90%                    | 暂停后台学习 / 降低标签页数                  |
| 内存 > 85%                   | 清理缓存 / 减少ChromaDB缓存                  |
| 内存 > 85%                   | Celery并发数从4降至1，暂停LoRA训练           |
| 磁盘 IO > 80%                | 延迟非关键写入                               |
| 网络带宽 > 设定上限          | 降低学习速率                                 |
+-----------------------------+---------------------------------------------+

### 4.1.4 自适应调整决策树

IF GPU_VRAM > 95%:
    APPLY int8_quantization()
    UNLOAD inactive_loras() TO ram
    IF STILL_OOM: ENABLE cpu_offload()
ELSE IF GPU_TEMP > 85度C:
    REDUCE batch_size BY 50%
    LOG thermal_throttle_event()
ELSE IF SYS_RAM > 85%:
    SET celery_concurrency = 1
    PAUSE lora_training_tasks()
ELSE:
    MAINTAIN optimal_performance_profile()

## 5.5 v2.3.1新增优化任务（5个详细卡片）

### TASK-LEARN-006：混合检索系统（Hybrid Search）

目标：提升RAG检索精度，解决专有名词、代码等精确匹配问题。

技术约束：
  - 引入全文搜索引擎（SQLite FTS5）
  - 保持与现有ChromaDB向量检索的并行调用

实现要求：
  1. 修改KnowledgeProcessingService，在知识入库时同步写入全文搜索引擎
  2. 重构KnowledgeInjectionService.retrieve方法，实现双路召回（向量+关键词）
  3. 实现RRF（Reciprocal Rank Fusion）算法融合重排序
     - 公式：score = 1/(k + rank_vector) + 1/(k + rank_keyword)，k=60
  4. 高级方案：使用Cross-Encoder模型（bge-reranker）对前50个候选精细化重打分

验收标准：
  - 专有名词测试集上，检索命中率（Hit Rate）提升 > 15%
  - 检索延迟增加 < 20ms


### TASK-LEARN-007：Agent分级决策机制

目标：优化AI浏览Agent决策速度，减少不必要的视觉理解开销。

技术约束：
  - 引入轻量级页面分类器
  - 不降低复杂页面的决策准确率

实现要求：
  1. 在BrowserAgentService中新增classify_page方法
  2. 页面复杂度分类器特征：
     - DOM结构：<form>标签数量、<input>类型、<button>数量
     - 内容密度：文本与HTML标签的比例
     - 样式特征：是否存在大量onclick事件或复杂CSS类名
  3. 分级决策：
     - 简单页面（博客/新闻/文档）：跳过截图和Qwen3-VL，仅基于DOM文本快速决策
     - 复杂页面（Web App/后台管理/社交媒体）：维持"DOM+视觉"双模决策

验收标准：
  - 简单页面单次决策时间从~3s降低至<500ms
  - 复杂页面决策准确率无明显下降


### TASK-LEARN-008：LoRA训练加速

目标：将LoRA微调时间从30min-2h缩短至15min-1h。

技术约束：
  - 利用Flash Attention-2优化注意力计算
  - 使用8-bit优化器减少显存占用

实现要求：
  1. 配置模型加载时启用attn_implementation="flash_attention_2"
  2. 将优化器从AdamW替换为bitsandbytes的AdamW 8-bit或PagedAdamW
  3. 优化DataLoader：num_workers>0，pin_memory=True
  4. 使用cosine_with_restarts或polynomial学习率调度器
  5. 在显存允许情况下增大gradient_accumulation_steps
  6. 使用accelerate配置启用DeepSpeed ZeRO-2或ZeRO-3

验收标准：
  - 相同数据集和硬件下，单epoch训练时间减少>30%
  - 最终模型PPL和生成质量无下降


### TASK-LEARN-009：浏览器进程池

目标：优化内置浏览器启动速度，实现"秒开"体验。

技术约束：
  - 应用启动时预初始化浏览器进程
  - 确保进程复用时的状态隔离（Cookie、缓存清除）

实现要求：
  1. 创建BrowserPool服务，在app/main.py启动事件中初始化空闲CEF进程
  2. 修改AutonomousLearningService，从BrowserPool获取/归还浏览器实例
  3. 实现会话结束后的状态清理（清除Cookie、LocalStorage、缓存）
  4. 实现会话快照与恢复：保存"干净"快照，后续启动直接恢复

验收标准：
  - 学习会话启动时浏览器就绪时间从<3s降低至<1s
  - 不同学习会话之间无Cookie或缓存数据泄露


### TASK-LEARN-010：知识图谱可视化

目标：提供知识关联的可视化视图，增强用户对知识库的理解。

技术约束：

  2. 新增图数据存储模块，保存实体和关系
  3. 新增API GET /api/v1/learn/knowledge/graph，返回关联节点和边
  4. 前端KnowledgeBrowser组件增加"图谱视图"切换
  5. 支持节点拖拽、缩放和点击查看详情

验收标准：
  - 能够成功从知识内容中抽取实体关系
  - 前端能正确渲染知识图谱，支持拖拽/缩放/点击

## 8.3 全部模块原理与实现细节（7个模块）

### 8.3.1 AI对话模块

原理：基于LLM的流式推理 + RAG检索增强 + Agent工具调用
算法：vLLM推理引擎，8K上下文窗口，FP16/INT8动态量化
实现：FastAPI SSE流式输出，ChromaDB Top-5检索，BGE-large-zh向量化

### 8.3.2 AI绘画模块

原理：扩散模型（Diffusion）去噪生成
算法：CLIP Encode -> UNet Denoise -> VAE Decode
实现：ComfyUI-Core嵌入式节点化工作流，ControlNet姿态控制，IP-Adapter风格迁移

### 8.3.3 漫剧创作模块

原理：分镜DSL解析 + 3D场景编排 + 视频扩散生成
算法：Three.js WebGL实时渲染，LTX-2 Diffusion Transformer视频生成
实现：自定义DSL解析器，WebGL浏览器内3D渲染，多镜头一致性光流约束

### 8.3.4 视频生成模块

原理：视频扩散模型 + 帧间一致性约束
算法：LTX-2 / Wan2.1 / CogVideoX 分块生成+重叠融合
实现：显存优化分块推理，FFmpeg 7.x后处理，AV1编码

### 8.3.5 知识学习模块

原理：Agent自主浏览 + RAG检索 + LoRA增量学习
算法：ReAct决策模式，SimHash去重，PPL好奇心驱动
实现：CEF浏览器内核，LangChain Agent，ChromaDB向量存储，QLoRA微调

### 8.3.6 模型管理模块

原理：优先级队列 + 显存协商 + ML预测预加载
算法：XGBoost时序预测，PPO强化学习调度优化
实现：SQLite元数据库，SHA256校验，热加载/冷卸载

### 8.3.7 视频风格模块

原理：LoRA低秩自适应微调 + 风格迁移
算法：LTX-2 LoRA微调，QLoRA 4bit量化
实现：peft库，bitsandbytes量化，FVD/SSIM质量评估


## 8.4 模块间协调机制

### 8.4.1 大模型互斥
  - 6x6互斥矩阵控制功能并发

  - 调度器统一管理资源分配

  - ML预测引擎：XGBoost预加载，预测准确率>85%
  - 协同调度引擎：PPO优化调度策略，效率提升>20%
  - 显存监控：毫秒级轮询，4级阈值（安全/警戒/危险/溢出）

### 8.4.3 知识反哺
  - RAG即时注入：对话前检索ChromaDB Top-5，<100ms
  - LoRA深度融入：训练数据>=100条触发微调，全功能使用
  - 知识生命周期：青年->成熟->沉淀->淘汰

### 9.1.4 跨语言数据格式规范

+------------------+----------------------------+---------------------------------------------------+
| 边界              | 数据格式                    | 说明                                               |
+------------------+----------------------------+---------------------------------------------------+
| TS -> Python API | JSON (UTF-8)               | Pydantic校验，自动OpenAPI文档                       |
| TS -> Python WS  | JSON (UTF-8)               | 进度推送、实时通知                                  |
| Python -> Rust   | PyO3自动转换               | list->Vec, bytes->&[u8]                            |
| Python -> C/C++  | pybind11/ctypes            | numpy array -> raw pointer（零拷贝）                |
| Python -> CUDA   | torch.Tensor               | GPU上直接传递                                      |
| Python -> CEF    | JavaScript绑定+JSON        | 注入JS/回调                                        |
| Python -> FFmpeg | subprocess+管道/文件路径    | 视频文件路径或raw管道                               |
| Python -> SQLite | SQLAlchemy ORM             | 不写裸SQL（除迁移脚本）                             |
| Python -> ChromaDB| Python SDK                | embedding + metadata dict                          |
| Python -> Redis  | Redis-py (async)           | Celery broker + 缓存                               |
+------------------+----------------------------+---------------------------------------------------+

Tauri IPC专用格式（TypeScript <-> Rust，依据文档C 3.2.1节）：
- 序列化：JSON (UTF-8)，字段命名camelCase
- 前端校验：Zod schema运行时校验
- 后端校验：Rust serde编译时校验 + 运行时类型守卫
- 事件格式：{event: string, payload: unknown, timestamp: ISO8601}
- IPC命令命名规范：{domain}_{action}_{resource}
- 示例：browser_acquire_instance, knowledge_import_file, model_load_checkpoint

时间格式：统一使用ISO 8601字符串（如2026-08-07T00:45:00Z），禁止使用时间戳整数。
空值处理：Python的None映射为JSON的null，禁止使用空字符串""代替null。

### 9.2.3 Python 3.12 编码铁律

【优势发挥】
- AI/ML生态无可替代：PyTorch、Transformers、LoRA、ChromaDB、Qwen推理全部用Python调用
- 开发速度极快：FastAPI路由、业务逻辑、知识管线用Python编写
- 动态类型+丰富标准库：数据预处理、文本清洗、正则抽取、知识图谱构建
- 异步IO成熟：FastAPI + uvicorn处理高并发API请求
- 胶水语言特性：通过ctypes/pybind11调用C/C++加速模块

【劣势规避】
- GIL限制CPU多线程：计算密集型任务一律用multiprocessing或ProcessPoolExecutor，禁止用threading做CPU密集计算
- 运行时性能差：循环超过10万次的操作必须用NumPy/Pandas向量化
- 类型安全弱：全部函数必须写type hints；启用mypy --strict做静态检查；Pydantic v2做所有数据模型校验
- 内存管理粗糙：大模型加载/卸载必须用 del model; torch.cuda.empty_cache(); gc.collect() 三件套
- 包管理混乱：锁定pip freeze > requirements.txt；生产环境用uv替代pip
- 异步陷阱：FastAPI路由中禁止调用同步阻塞函数；所有IO操作必须用async/await

【正确示例】
async def retrieve_knowledge(query: str, top_k: int = 5) -> list[KnowledgeChunk]:
    embeddings: np.ndarray = await embedding_model.encode_async(query)
    results: list[KnowledgeChunk] = await vector_db.search(embeddings, top_k)
    return results

【禁止示例】
def retrieve_knowledge(query, top_k=5):
    results = []
    for chunk in all_chunks:  # 10万次循环，性能灾难
        score = manual_cosine(query, chunk)
        results.append((chunk, score))
    return sorted(results, key=lambda x: x[1], reverse=True)[:top_k]

- React生态：组件化UI、虚拟DOM高效渲染

### 9.2.5 Rust 1.75+ 编码铁律

【优势发挥】
- 零成本抽象+无GC：Tauri核心运行时、窗口管理、系统托盘、全局快捷键
- 内存安全无数据竞争：浏览器进程池管理、多进程通信、文件系统监控
- 极致性能：大文件哈希计算、AV1编码调度、模型文件IO
- FFI能力：作为Python/C++之间的桥梁，安全地传递数据

【劣势规避】
- 学习曲线陡峭：Rust代码只由核心开发者编写；限定在Tauri层和性能关键路径
- 编译速度慢：模块化拆分crate；开发时用cargo check替代cargo build；CI用sccache缓存

#[derive(Debug, thiserror::Error)]
pub enum BrowserPoolError {
    #[error("No available browser instance")]
    PoolExhausted,
    #[error("Browser process crashed: {0}")]
    ProcessCrashed(String),
    #[error("Timeout waiting for browser: {0}ms")]
    Timeout(u64),
}

pub async fn acquire_browser(&self) -> Result<BrowserInstance, BrowserPoolError> {
    let instance = self.pool.pop()
        .ok_or(BrowserPoolError::PoolExhausted)?;
    instance.health_check().await
        .map_err(|e| BrowserPoolError::ProcessCrashed(e.to_string()))?;
    Ok(instance)
}

### 9.4.3 基础安装包结构（~5GB）

仅包含app/、cef/、runtimes/，不含models/。
首次启动时引导用户选择：下载模型（断点续传）或指定本地已有模型路径。

### 9.4.4 运行时架构

Main Process (Tauri 2.x Rust壳)
├── 前端渲染进程（React应用）
│   └── WebView2 / CEF渲染
├── 后端进程（Python/FastAPI，Uvicorn）
│   ├── 监听 127.0.0.1:8000
│   ├── Celery Beat（定时任务调度）
│   ├── Celery Workers（异步任务执行，按需启动，绑定GPU设备）
│   ├── BrowserAgent（AI浏览Agent）
│   └── Scheduler（智能调度引擎）
├── CEF进程（Chromium 120+，独立渲染进程）
│   └── 受BrowserPool进程池管理
├── AI推理进程（PyTorch模型推理）
│   └── 由Worker懒加载，首次请求时载入显存
└── 模型管理器（GPU显存监控+模型生命周期）

### 9.4.5 安装流程

1. 运行安装程序（installer.exe）
2. 系统检查：
   - Windows 10 21H2+ / Windows 11 64位
   - 磁盘空间 >= 450GB（完整包）或 >= 50GB（基础包）
   - 内存 >= 32GB
   - GPU检测：NVIDIA/AMD/纯CPU
3. 解压文件到目标目录
4. 注册文件关联（.omni项目文件）
5. 创建桌面快捷方式和开始菜单条目
6. 首次启动：引导用户完成基础配置（语言、存储路径、GPU设置）

### 9.4.6 更新与升级策略

增量更新：基于zsync或自定义二进制差分算法，仅更新变化的文件块。
回滚机制：更新前自动备份app/和config/；若新版本启动失败3次，自动回滚至上一版本。
模型更新：通过HuggingFace镜像下载增量模型权重，SHA256校验后替换。
版本检查：启动时对比本地版本号与服务器最新版本，提示用户更新。

## A.2 ADR-01 详细记录：3D导演台技术选型

问题：3D导演台应使用何种渲染技术？

候选方案：
方案A：Unity 引擎（独立渲染进程）
方案B：Blender Headless（Python脚本驱动）
方案C：Three.js r170（WebGL浏览器内渲染）

评估维度：
+------------------+------------+------------+------------+
| 维度              | Unity      | Blender    | Three.js   |
+------------------+------------+------------+------------+
| 渲染性能          | 优秀        | 良好        | 良好        |
+------------------+------------+------------+------------+
| 显存占用          | 高(独立进程) | 高(独立进程) | 低(共享WebView)|
+------------------+------------+------------+------------+
| 与前端集成度      | 差(需IPC)   | 差(需IPC)   | 优(同进程)   |
+------------------+------------+------------+------------+
| 开发效率          | 中          | 低          | 高          |
+------------------+------------+------------+------------+
| 包体积            | 大(+2GB)    | 大(+1.5GB)  | 小(0额外)    |
+------------------+------------+------------+------------+
| 许可证成本        | 高(商业授权) | 免费        | 免费(MIT)   |
+------------------+------------+------------+------------+
| 社区生态          | 丰富        | 丰富        | 极丰富       |
+------------------+------------+------------+------------+

决策：选择方案C（Three.js r170 WebGL浏览器内渲染）

理由：
1. 与React前端渲染管线深度集成，无需独立进程，显存占用减半
2. 零额外包体积（已在Tauri WebView中）
3. MIT许可证，无商业授权成本
4. 社区活跃，WebGL生态成熟
5. 满足所有3D导演台功能需求（资产加载、场景管理、相机控制、实时预览）
6. 通过 React Three Fiber + @react-three/drei 声明式封装 Three.js，与 React 组件树深度集成，状态驱动 3D 场景

## A.3 ADR-02 详细记录：桌面壳层选型

问题：桌面壳层应使用何种技术？

候选方案：
方案A：Electron
方案B：Tauri 2.x (Rust)
方案C：原生WinUI

评估维度：
+------------------+------------+------------+------------+
| 维度              | Electron   | Tauri 2.x  | WinUI      |
+------------------+------------+------------+------------+
| 内存占用          | 高(~500MB) | 低(~150MB) | 极低(~50MB)|
+------------------+------------+------------+------------+
| 包体积            | 大(~200MB) | 小(~5MB)   | 中(~50MB)  |
+------------------+------------+------------+------------+
| 跨平台            | 优秀        | 良好        | 差(仅Win)   |
+------------------+------------+------------+------------+
| 前端兼容性        | Chromium   | WebView2   | 需自建     |
+------------------+------------+------------+------------+
| 系统API访问       | Node.js    | Rust原生   | C++原生    |
+------------------+------------+------------+------------+
| 安全性            | 中          | 高(内存安全) | 中          |
+------------------+------------+------------+------------+
| 开发效率          | 高          | 中          | 低          |
+------------------+------------+------------+------------+

决策：选择方案B（Tauri 2.x Rust）

理由：
1. Rust内存安全，消除数据竞争和空指针风险
2. 包体积仅5MB，远小于Electron的200MB
3. 内存占用仅150MB，较Electron降低60%以上
4. 原生系统API访问（窗口管理、全局快捷键、系统托盘）
5. 可直接管理CEF浏览器进程池
6. 与Python/C++通过FFI桥接，Rust作为安全中间层
