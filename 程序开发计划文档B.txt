OmniSpace AI v2.3.1 程序开发计划文档（Part I — 项目全量与调度方案）
第一章 项目全量信息
1.1 产品定义
属性	描述
产品名称	OmniSpace AI v2.3.1
产品类型	AIGC 桌面创作工具 + 自主学习 AI 助手
核心价值	为影视创作者提供离线化、智能化、一站式的 AIGC 创作流，通过自主学习引擎实现个性化模型进化与创作辅助。
运行环境	Windows 10 21H2+ / Windows 11 64位 (x64)
分发方式	完整离线安装包 (~392GB) 或 基础安装包 (~5GB) + 用户手动导入模型
1.2 六大核心模块详解
1.2.1 AI对话模块 (OmniChat)
技术选型: Qwen3-VL-8B / Qwen3-VL-4B / Qwen3-VL-2B (vLLM 推理后端)
功能清单: 多模态对话、剧本润色、分镜描述生成、Agent 工具调用、上下文记忆。
输入输出: 文本/图像输入 -> 文本/JSON/Markdown 输出。
依赖关系: 依赖 ModelManager 进行权重加载，依赖 LearningEngine 获取 RAG 知识。
1.2.2 AI绘画模块 (OmniDraw)
技术选型: FLUX.1-dev / Kolors 2.1 / SDXL + ControlNet + IP-Adapter (ComfyUI-Core 嵌入式)
功能清单: 文生图、图生图、ControlNet 姿态控制、IP-Adapter 风格迁移、局部重绘。
输入输出: Prompt/参考图/ControlMap -> 高分辨率图像 (PNG/EXR)。
依赖关系: 依赖 ModelManager，依赖 OmniChat 进行 Prompt 扩写。
1.2.3 漫剧创作模块 (OmniComic)
技术选型: 分镜表引擎 + 3D导演台 (Three.js r170 (WebGL in-browser rendering)) + 视频生成 (LTX-2 / Wan2.1 / CogVideoX)
说明: Three.js r170 基于 WebGL 在浏览器内完成 3D 场景渲染，无需独立渲染进程，与前端渲染管线深度集成。
【7步操作流程（详见OmniComic完整需求规格说明书）】：
  步骤1-创建项目：名称唯一性校验、模板选择（空白/漫剧模板）、项目管理
  步骤2-导入剧本：DSL文件上传(.txt≤10MB)、DSL文本粘贴、手动自由文本输入、NLP语义分析
  步骤3-自动/手动分镜：自动逐镜生成分镜卡片、手动四种添加方式、拖拽排序、模式切换
  步骤4-生成资产图：角色图(4096×1024横排4格多视图)、场景图、道具图 + 角色音色绑定(1默认+N情感两层)
  步骤5-分镜描述词：AI辅助生成分镜描述、风格一致性(IP-Adapter统一seed)
  步骤6-导演台操作：3D场景编排、自动资产拉取→3D内容生成、四分镜合一图展示、WebGL不支持时降级为2D分镜图
  步骤7-视频生成：三路输入(分镜图+资产图+描述词)、LTX-2/Wan2.1/CogVideoX、<60s/5秒片段
功能清单: 分镜脚本解析、3D 资产编排、视频片段生成、多镜头一致性控制、角色多视图设定图、音色绑定。
输入输出: 结构化剧本/3D场景 -> 视频序列/分镜图。
依赖关系: 强依赖 OmniDraw (关键帧)，依赖 VideoStyleEngine (风格统一)。
1.2.4 知识学习模块 (OmniLearn) v2.3新增
技术选型: Chromium Embedded Framework (CEF) + LangChain Agent + LoRA Evolution Pipeline
功能清单: 内置浏览器网页解析、资料结构化、Agent 自动摘要、LoRA 增量训练触发。
输入输出: URL/本地文档/剪贴板 -> 结构化知识库/LoRA 权重。
依赖关系: 依赖 LearningEngine 调度，依赖 ModelManager 存储训练产物。
1.2.5 模型管理模块 (ModelManager)
技术选型: 自研分布式存储调度器 + SQLite 元数据库
功能清单: ~392GB 模型库索引、三方协同调度、Hash 校验、热加载/冷卸载。
输入输出: 模块请求 -> 模型句柄/显存映射。
依赖关系: 被所有创作模块依赖，依赖 MLPredictEngine 进行预加载。
1.2.6 视频风格模块 (VideoStyle)
技术选型: LTX-2 LoRA 微调引擎 + FFMPEG
功能清单: 视频风格 LoRA 训练、推理应用、帧间一致性处理。
输入输出: 视频片段/参考图 -> 风格化视频/LoRA 权重。
依赖关系: 依赖 LearningEngine 获取训练数据，依赖 AV1Encoder 输出。
1.3 五大智能引擎详解
引擎名称	技术原理	触发条件	执行流程
LTX-2 LoRA微调引擎	基于 LTX-2 的 Diffusion Transformer 微调，支持显存分块训练	用户在 VideoStyle 或 OmniLearn 提交训练任务	数据预处理 -> 显存分配 -> 梯度累积 -> Checkpoint 保存 -> 验证
模型预加载ML预测引擎	XGBoost 时序预测模型，基于历史操作序列预测下一模型	用户完成当前操作或空闲 >500ms	特征提取 -> 模型推理 -> 置信度过滤 -> 异步加载至显存
协同调度历史学习引擎	强化学习 (PPO) 优化资源分配策略	系统资源冲突或任务完成反馈	状态观测 -> 策略网络 -> 动作执行 -> 奖励计算 -> 策略更新
AV1硬件编码引擎	硬件加速 API 封装 + SVT-AV1 软编降级	视频生成/导出任务启动	硬件探测 -> 编码器选择 -> 码率控制 -> 帧级编码 -> 封装
自主学习引擎	RAG + Agent 决策树 + 增量学习闭环	用户授权学习或检测到新知识源	内容抓取 -> 知识抽取 -> 入库 -> 触发微调/更新 RAG 索引
1.4 核心约束
硬件底线: NVIDIA RTX 3060 12GB / RTX 4060 8GB (最低显存)，推荐 RTX 4090 24GB / RTX 5090 32GB。系统内存 ≥32GB。
软件依赖: Windows 10 21H2+ / Win11, NVIDIA Driver ≥535.xx, CUDA 12.1+, DirectX 12, AV1 Codec 支持。
网络要求: 核心功能 100% 离线可用。仅 OmniLearn 网页抓取及可选的遥测数据需网络。
安全边界: 本地沙箱隔离浏览器进程；LoRA 训练数据仅存本地；禁止未经授权的模型外传。

第四章 调整方案
4.1 性能自适应调整方案
4.1.1 GPU显存监控与自适应降参策略
系统需实现毫秒级显存监控，根据当前占用率动态调整模型推理参数，防止OOM（Out Of Memory）崩溃。
显存使用率阈值	状态定义	精度降级策略	模型卸载策略
< 70%	安全区	维持 fp32/bf16	全量驻留显存
70% - 85%	警戒区	降级至 fp16	保持全量驻留，开启显存碎片整理
85% - 95%	危险区	降级至 bf16/int8	卸载非活跃LoRA权重至内存
> 95%	溢出区	强制 int8 量化推理	卸载基础模型至内存，启用CPU Offload
4.1.2 CPU与内存自适应
针对Celery后台任务与前端渲染的内存竞争，实施以下自适应机制： - 内存占用阈值：当系统总内存占用 > 85% 时，触发内存保护机制。 - 进程优先级调整：使用 os.nice() 降低非关键Celery Worker的CPU调度优先级，保障前端React 19.2主线程与Three.js渲染的60FPS流畅度。 - 后台任务 Throttling：当内存告警时，动态调整Celery并发数（concurrency 从 4 降至 1），并暂停非紧急的LoRA训练任务。
4.1.3 温度与功耗自适应
通过 pynvml 或 rocm-smi 轮询硬件状态： - GPU温度阈值：> 85°C 触发降频，> 90°C 强制暂停生成任务并弹出UI警告。 - 功耗墙处理：当检测到功耗触及TDP上限且温度升高时，自动将推理Batch Size减半。 - 降频策略：记录连续3次高温降频事件后，在当前会话内锁定最大GPU利用率至 80%。
4.1.4 自适应调整决策树
IF GPU_VRAM > 95%:
    APPLY int8_quantization()
    UNLOAD inactive_loras() TO ram
    IF STILL_OOM: ENABLE cpu_offload()
ELSE IF GPU_TEMP > 85°C:
    REDUCE batch_size BY 50%
    LOG thermal_throttle_event()
ELSE IF SYS_RAM > 85%:
    SET celery_concurrency = 1
    PAUSE lora_training_tasks()
ELSE:
    MAINTAIN optimal_performance_profile()

4.3 学习策略调整方案
4.3.1 知识库容量自适应
阈值设定：向量库条目 < 10k 时全量加载；10k-100k 时启用ChromaDB HNSW索引；> 100k 时切换至ChromaDB/SQLite FTS5混合检索。
学习速率调整：知识库增量 > 1k/天时，自动降低LoRA训练Epoch数，防止灾难性遗忘。
数据保留策略：采用LRU算法，自动归档30天未命中的旧知识片段至冷存储。
4.3.2 LoRA训练质量自适应
评估指标：实时监控 Validation Loss，若连续5个Step无下降，触发超参数微调。
自动调优：Loss震荡时自动降低 Learning Rate (乘以0.8)；Loss停滞时尝试增加 Rank 维度。
早停策略：Validation Loss 回升超过 5% 立即停止训练，保存最优Checkpoint。
4.3.3 网络状况自适应
带宽监测：通过 speedtest-cli 或系统API实时获取下行带宽。
下载限速：带宽 < 10Mbps 时，限制HuggingFace模型下载并发数为1，并启用断点续传。
离线模式：网络断开时，自动切换至本地缓存模型，禁用在线RAG检索，UI显示离线标识。
4.3.4 用户行为自适应
偏好分析：统计用户高频使用的Prompt标签与生成参数，构建用户画像向量。
主动学习：当检测到用户在特定领域（如“赛博朋克”）频繁微调时，主动推荐相关开源LoRA。
好奇心驱动：在空闲状态下，利用强化学习探索用户未触及的模型组合，生成惊喜推荐。

7.1 完整后端架构总览
7.1.1 后端服务进程模型
Main Process：Uvicorn 主进程，处理 HTTP/WebSocket 请求。

7.1.2 进程间通信机制（含Tauri IPC规范）
【桌面壳层】Tauri 2.x (Rust) 原生层架构：
- 窗口管理：Rust 原生窗口管理，通过 Tauri API 创建/销毁/管理窗口生命周期
- IPC 通信：Tauri Command 机制，前端 invoke() 调用 Rust 后端，JSON + camelCase + Zod/serde 双向验证
- 浏览器进程池：Rust 侧管理 CEF 进程池生命周期，通过 Tauri sidecar 或子进程方式启动
- Rust 代码占比：约 12%（窗口管理、IPC、浏览器进程池、AV1 编码桥接）

【后端服务间通信】
Redis：Celery Broker、任务状态存储、全局缓存。
WebSocket：前端实时进度推送（通过 Tauri IPC 桥接至渲染进程）。
HTTP REST：常规 CRUD 操作（base URL: http://localhost:8000/api/v1）。

【Tauri IPC 协议规范】（参照文档C 3.2.1节）
- 消息格式：JSON，字段命名 camelCase
- 前端→Rust：window.__TAURI__.invoke('command_name', { payload })
- Rust→前端：通过 Tauri Event 系统 emit 事件
- 验证层：前端 Zod schema 验证入参，Rust 侧 serde Deserialize 验证
- 错误处理：Rust 侧使用 thiserror 定义错误类型，统一序列化为 JSON error 返回
- 示例：
  // 前端调用
  const result = await invoke('load_model', { modelId: 'qwen3-vl-8b', quantize: 'int8' });
  // Rust 侧
  #[tauri::command]
  async fn load_model(model_id: String, quantize: String) -> Result<ModelHandle, AppError> { ... }

8.4 七大核心模块原理与实现细节
8.4.1 自主学习引擎
原理：基于 LLM 的 Goal-Setting 与 ReAct 模式。
算法：PPL (Perplexity) 驱动的好奇心探索 + 知识图谱覆盖率奖励。
8.4.2 LoRA微调引擎
原理：Low-Rank Adaptation，冻结预训练权重，仅训练低秩分解矩阵。
实现：peft 库 + bitsandbytes 4-bit 量化。
8.4.3 模型预加载引擎
原理：XGBoost 预测用户未来 5 分钟可能使用的模型。
特征：时间、当前页面、历史频率、显存余量。
8.4.4 协同调度引擎
算法：Priority Queue + Resource Reservation。
冲突解决：训练任务优先级低于推理，显存不足时自动 Offload。
8.4.5 AV1编码引擎
切换：检测 NVIDIA RTX 30+ 使用 NVENC，否则 SVT-AV1 CPU。
调优：CRF 23, Preset 6, Keyint 240。
8.4.6 CEF浏览器引擎
管理：Object Pool 模式，复用 Render Process。
过滤：Rust 编写的 AdBlock 引擎，注入 CSS/JS 拦截。
8.4.7 知识处理引擎
RAG：HyDE (Hypothetical Document Embeddings) 增强检索。
注入：System Prompt 动态拼接 + LoRA Adapter 热切换。
8.5 模块间协调机制
事件总线：Redis Pub/Sub，Topic: omnispace.events。
消息格式：{"event": "model.loaded", "data": {"id": "llama-3", "vram": 12000}}。
依赖：KnowledgeInjectionService 依赖 KnowledgeProcessingService 的完成事件。

9.1.4 跨语言数据格式规范
Python ? TypeScript: 使用 Pydantic V2 定义 Schema，通过 FastAPI 自动生成 OpenAPI JSON，前端使用 openapi-typescript-codegen 生成 TS 接口。
Python ? C++ (CEF): 采用 JSON 字符串序列化。C++ 端使用 nlohmann/json 解析，禁止使用二进制协议以降低跨语言维护成本。

9.2 编程语言规范
9.2.1 Python 规范
【编码铁律（文档C）】async/await 强制 + type hints 强制 + mypy strict 模式
PEP 8 扩展: 行宽限制 120 字符；强制使用 Type Hints（包括返回值），所有函数签名必须通过 mypy --strict 检查；禁止 *args/**kwargs 除非作为装饰器或底层框架桥接。
异步编程: 所有 I/O 操作必须使用 async/await；禁止在异步上下文中调用同步阻塞函数（如 time.sleep、requests.get）；FastAPI 路由函数必须声明为 async def。
异常处理: 禁止裸 except:；必须捕获具体异常；业务异常继承 OmniSpaceBaseException；使用自定义异常层次结构。
日志规范: 使用 structlog，禁止 print()；日志必须包含 task_id 和 trace_id 字段。
类型检查: CI 中强制运行 mypy --strict，不允许 type: ignore 注释。
9.2.2 TypeScript 规范
【编码铁律（文档C）】no-any 强制 + Zod schema 验证
命名约定: 接口/类型使用 PascalCase（IUserProfile）；变量/函数使用 camelCase；常量使用 UPPER_SNAKE_CASE。
类型定义: 严格禁止使用 any 类型；使用 Zod 定义运行时验证 schema，与 TypeScript 类型保持同步；优先使用 interface 而非 type；组件 Props 必须定义独立接口。
错误处理: 使用 React Error Boundary 捕获渲染错误；API 调用统一封装在 apiClient.ts 中处理拦截器；所有 API 返回值使用 Zod parse 验证。
ESLint: 配置 @typescript-eslint/no-explicit-any: error，禁止绕过类型检查。
9.2.3 C++ 规范 (CEF 绑定层)
【编码铁律（文档C）】RAII 强制 + smart pointers 强制
内存管理: 严格遵循 RAII 原则；禁止使用 new/delete，统一使用 std::unique_ptr / std::shared_ptr；严格遵循 Chromium 的 scoped_refptr 和引用计数机制；禁止裸指针跨线程传递。
命名空间: 所有自定义代码必须包裹在 namespace omnispace::cef { ... } 中。
线程安全: UI 操作必须在 CEF UI Thread 执行；通过 CefPostTask 进行线程调度。
编译: 启用 -Wall -Wextra -Werror，CI 中 clang-tidy 检查。
9.2.4 SQL 规范 (SQLAlchemy 2.0)
【编码铁律（文档C）】参数化查询强制，禁止字符串拼接
模型定义: 必须继承 Base；所有表必须包含 id, created_at, updated_at 字段。
迁移规范: 使用 Alembic；禁止手动修改数据库；每个迁移文件必须包含 upgrade() 和 downgrade()。
查询规范: 严格禁止原生 SQL 字符串拼接（防止 SQL 注入）；必须使用 ORM 表达式或 text() 显式声明参数绑定；安全审计工具 bandit 配置 B608 规则为 error 级别。
SQLite 特定: PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON;
9.2.5 Rust 规范 (Tauri 2.x 原生层)
【编码铁律（文档C）】thiserror 强制 + no-unwrap 强制
错误处理: 所有错误必须使用 thiserror crate 定义结构化错误类型，禁止使用 unwrap()/expect()，统一使用 ? 操作符传播错误。
类型安全: 所有跨 FFI 边界的数据结构必须实现 serde::Serialize + Deserialize，使用 Zod（前端）与 serde（Rust 端）双向验证。
命名规范: 模块使用 snake_case，结构体/枚举使用 PascalCase（CamelCase），函数使用 snake_case。
异步: 使用 tokio 运行时，所有 I/O 操作使用 async fn。
内存: 禁止 unsafe 块，除非经团队 Code Review 批准并附详细注释说明安全性。
测试: 所有 pub 函数必须有单元测试，使用 #[cfg(test)] 模块。
CI: cargo clippy -- -D warnings 强制，cargo fmt --check 强制。

9.2.6 Shell/Bash 规范
脚本首行必须声明 #!/usr/bin/env bash 和 set -euo pipefail。
变量必须使用双引号包裹 "$VAR"。
禁止使用 cd 改变全局目录，使用子 shell (cd /path && cmd)。
9.2.7 JSON/YAML 配置规范
键名统一使用 snake_case。
YAML 文件必须包含头部注释说明用途。
敏感配置（API Key、密码）禁止硬编码，必须使用环境变量或 .env 文件。
9.2.8 Markdown 文档规范
标题层级不得跳级（如 # 后直接 ###）。
代码块必须标注语言（如 ```python）。
图片必须包含 Alt 文本：![描述](路径)。
9.2.9 测试代码规范
