# OmniSpace AI v2.3.1 编程语言规范与协同方案

一、语言总览与职责边界

本项目涉及 8 种编程语言 / 技术语言，每种语言有且仅有一个不可替代的职责域。核心原则：让每种语言只做它最擅长的事，绝不让它越界。
语言   角色定位   占比（代码行）
Python 3.12   后端主语言 / AI推理 / 训练引擎   ~45%

TypeScript 5.x   前端主语言 / UI逻辑 / 类型安全   ~25%

Rust 1.75+   Tauri原生层 / 系统级性能 / 安全   ~12%

C/C++   CUDA加速 / CEF浏览器底层 / 编解码   ~8%

SQL (SQLite)   数据持久化 / 全文检索   ~3%

HTML5 + CSS3   视图渲染 / 视觉表现   ~4%

Shell (Bash/PowerShell)   构建 / 部署 / 自动化脚本   ~2%

JSON / YAML   配置 / 数据交换 / 模型元数据   ~1%

二、各语言优势发挥与劣势规避

2.1 Python 3.12（后端核心）

✅ 优势发挥
优势   项目中的应用
AI/ML生态无可替代   PyTorch、Transformers、LoRA、ChromaDB、Qwen推理全部用Python调用

开发速度极快   FastAPI路由、业务逻辑、知识管线用Python编写，迭代效率最高

动态类型+丰富标准库   数据预处理、文本清洗、正则抽取、知识图谱构建

异步IO成熟   FastAPI + uvicorn 处理高并发API请求

胶水语言特性   通过ctypes/pybind11调用C/C++加速模块

❌ 劣势规避
劣势   规避策略
GIL限制CPU多线程   计算密集型任务（向量检索、知识抽取）一律用 multiprocessing 或 concurrent.futures.ProcessPoolExecutor，禁止用threading做CPU密集计算

运行时性能差   任何循环超过10万次的操作，必须用NumPy/Pandas向量化，禁止纯Python for循环处理大批量数据

类型安全弱   全部函数必须写type hints；启用 mypy --strict 做静态检查；Pydantic v2做所有数据模型校验

内存管理粗糙   大模型加载/卸载必须用 del model; torch.cuda.empty_cache(); gc.collect() 三件套；禁止在循环中重复加载模型

包管理混乱   锁定 pip freeze > requirements.txt；生产环境用 uv 替代pip；禁止 pip install 不指定版本

异步陷阱   FastAPI路由中禁止调用同步阻塞函数；所有IO操作必须用 async/await；数据库操作统一用 aiosqlite

✅ 正确：向量化 + 类型标注 + 异步
async def retrieve_knowledge(query: str, top_k: int = 5) -> list[KnowledgeChunk]:

✅ 优势发挥
优势   项目中的应用
静态类型系统   所有组件Props、API响应、状态管理全部强类型定义，编译期消灭90%的运行时错误

❌ 劣势规避
劣势   规避策略
类型系统可被 any 绕过   ESLint配置 @typescript-eslint/no-explicit-any: error，禁止使用any，必须用 unknown + 类型守卫

回调地狱   禁止嵌套超过2层的回调；统一用async/await；错误统一用ErrorBoundary捕获

// ✅ 正确：明确错误类型 + 所有权清晰 + 无unwrap
[derive(Debug, thiserror::Error)]
pub enum BrowserPoolError {
    #[error("No available browser instance")]
    PoolExhausted,
    #[error("Browser process crashed: {0}")]
    ProcessCrashed(String),
    #[error("Timeout waiting for browser: {0}ms")]
    Timeout(u64),
}

pub async fn acquire_browser(&self) -> Result<BrowserInstance, BrowserPoolError> {
    let instance = self.pool.pop()
        .ok_or(BrowserPoolError::PoolExhausted)?;
    instance.health_check().await
        .map_err(|e| BrowserPoolError::ProcessCrashed(e.to_string()))?;
    Ok(instance)
}

// ❌ 禁止：unwrap + panic + 裸指针
fn acquire_browser(&self) -> BrowserInstance {
    self.pool.pop().unwrap() // 生产环境崩溃
}

3.2 语言间通信协议规范

3.2.1 TypeScript ↔ Rust（Tauri IPC）

通信方式：Tauri invoke / event
数据格式：JSON（自动序列化/反序列化）
类型保障：TS端用Zod校验，Rust端用serde反序列化

规则：
每个IPC命令必须有明确的输入/输出类型定义
TS端定义 interface，Rust端定义对应 struct，字段名必须一致（camelCase）
错误必须结构化返回，禁止字符串拼接错误信息
大数据（>1MB）不走IPC，改用文件路径传递
异步IPC必须设置超时（默认30s）

IPC命令命名规范：
{domain{action}{resource}

示例：
browser_acquire_instance
browser_release_instance
knowledge_import_file
model_load_checkpoint
system_get_gpu_info

IPC数据结构示例：
// TypeScript端

3.2.3 Python ↔ C/C++（pybind11）

通信方式：pybind11 FFI调用
数据格式：NumPy数组 / py::buffer / py::object
内存管理：C++端不持有Python对象引用；数据拷贝最小化

规则：
C++函数接收numpy数组，返回numpy数组
禁止在C++层抛出Python异常；用返回值或错误码
GPU内存分配/释放必须在同一个C++函数内完成（RAII）
pybind11模块命名omnispace{module}（下划线前缀表示内部模块）
每个pybind11模块必须有对应的Python类型存根（.pyi文件）

pybind11接口规范：
// C++端：返回错误码 + 输出参数
int resize_image(
    pybind11::array_t<uint8_t> input,   // 输入图像 [H,W,C]
    int target_w, int target_h,
    pybind11::array_t<uint8_t>& output  // 输出图像
);
// 返回值：0=成功，负数=错误码

Python端：包装为Pythonic接口
def resize_image(image: np.ndarray, target_w: int, target_h: int) -> np.ndarray:
    output = np.empty((target_h, target_w, image.shape[2]), dtype=np.uint8)
    code = _omnispace_vision.resize_image(image, target_w, target_h, output)
    if code != 0:
        raise VisionProcessingError(f"Resize failed with code {code}")
    return output

3.2.4 Rust ↔ Python（进程间通信）

通信方式：HTTP（Python FastAPI作为独立进程）
启动方式：Rust/Tauri启动时spawn Python进程
健康检查：每5秒 GET /health
数据格式：JSON over HTTP

规则：
Python进程由Rust管理生命周期（启动/监控/重启/优雅关闭）
Python进程崩溃时，Rust必须在3秒内检测并重启
模型加载/卸载由Python进程自行管理，Rust不干预
进程间禁止共享内存（避免GIL和所有权冲突）

3.2.5 全语言间数据格式对照
场景   格式   序列化方   反序列化方

TS→Python API   JSON (camelCase)   JS原生   Pydantic v2

模型元数据   JSON   Python生成   全语言读取

3.3 跨语言错误处理链

错误传播原则：每一层只包装自己领域的错误，不吞掉底层错误信息。

C++层：返回错误码（int）+ 错误描述（string）
    ↓ pybind11 转换为 Python异常
Python层：捕获 → 包装为业务异常（如 ModelInferenceError）→ 返回HTTP错误响应
    ↓ JSON error字段
TypeScript层：解析error → 用户友好提示 + 控制台详细日志
    ↓ 如果是系统级错误
Rust层：记录到本地日志文件 + 可选上报

错误码全局注册表：
  1xxx - 模型相关（加载/推理/显存）
  2xxx - 知识相关（入库/检索/图谱）
  3xxx - 浏览器相关（启动/导航/Agent）
  4xxx - 训练相关（LoRA/数据/评估）
  5xxx - 系统相关（文件/进程/配置）
  6xxx - 前端相关（渲染/状态/IPC）

3.4 跨语言性能边界规则
规则   说明
数据不过境   大模型权重（~30GB）绝不通过IPC/HTTP传输；Python进程直接加载本地文件

小数据JSON   <1MB的结构化数据用JSON；>1MB用文件路径引用

图像走buffer   图像数据在Python↔C++之间用numpy buffer零拷贝传递，禁止Base64编码

向量走二进制   1024维float32向量（4KB）在Python内部处理；传给前端时只传相似度分数，不传原始向量

流式走SSE   AI对话token流用SSE推送；禁止轮询；禁止WebSocket传token流

批量走文件   批量导入知识（>100条）用文件上传，禁止循环调用单条API

四、语言间禁止事项总表
编号   禁止事项   原因
F-001   Python中用threading做CPU密集计算   GIL限制，无并行效果

F-002   TypeScript中使用 any 类型   消灭类型安全

F-003   Rust业务代码中使用 unwrap()   生产环境panic崩溃

F-004   C++中使用裸 new/delete   内存泄漏风险

F-005   SQL字符串拼接   SQL注入

F-006   前端直接操作SQLite数据库文件   绕过权限控制，数据损坏

F-007   Rust主线程做阻塞IO   UI冻结

F-008   Python asyncio循环中调用同步函数   事件循环阻塞

F-009   IPC传递>1MB的JSON数据   序列化/反序列化性能瓶颈

F-010   C++层创建独立CUDA context   与Python CUDA context冲突，显存翻倍

F-011   前端用WebSocket传AI token流   应用SSE，WebSocket过重

F-012   Shell脚本超过50行   可维护性差，改用Python

F-013   JSON配置文件中存放大段文本   改用YAML或数据库

F-014   跨语言传递Python对象（pickle）   不安全，用JSON

F-015   多进程同时写同一个SQLite文件   单写锁冲突，数据损坏

六、总结：语言协同黄金法则

1. 单一职责：每种语言只做它最擅长的事，绝不越界。
2. 边界清晰：语言之间的接口必须有明确的类型契约（schema），不允许"默契"。
3. 数据不过境：大数据（模型、图像、视频）通过文件/共享内存传递，不通过IPC/JSON。
4. 错误不吞没：每一层包装自己的错误，但必须保留底层错误链。
5. 性能不妥协：性能热点用C++/Rust，业务逻辑用Python/TS，绝不用慢语言做快语言的事。
6. 类型不绕过：Python用mypy，TS用strict，Rust用编译器，C++用sanitizer。四道防线，缺一不可。
7. 构建可复现：所有依赖版本锁定，构建顺序固定，任何环境可一键复现。
